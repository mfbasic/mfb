# bug-768: `removeKey` / Set `remove` on a record or `STATE` field slides every later entry — O(n) per removal, ~40× the same removal on a local

Last updated: 2026-09-28
Effort: large (3h–1d)
Severity: MEDIUM
Class: Other (Performance)

Status: Open
Regression Test: planned `tests/runtime/rt_map_field_fifo_removal_flat.rs` (cost) and
`tests/runtime/rt_inplace_field_tombstone_invisible.rs` (correctness)

bug-760 B1 (`8f069dc0f`) made an in-place `removeKey` / Set `remove` at a probed
**binding** (local, global, by-reference capture) leave a tombstone and compact lazily,
so removing the oldest key costs O(1) amortized. The same self-update at a **record or
`STATE` field** (`rec = WITH rec { xs := collections::removeKey(rec.xs, k) }`,
`f.state.xs = collections::removeKey(f.state.xs, k)`) was deliberately left on bug-732's
slide: every entry after the removed one is copied down one slot, its key re-hashed
and its bucket renumbered. Removing in insertion order (FIFO, sliding window, the
benchmark's front-removal loop) therefore costs the window size per step. The field
rows are now ~13× the plain rows in the benchmark, and 10× slower per step for 8× the
window in a standalone probe.

**The single correct behavior a fix produces:** removing the oldest key of a
`Map`/`Set` held in a record or `STATE` field costs the same per step at any window
size (FIFO W=4000 per-step time ≤ 3× W=500, the bound `rt_map_fifo_removal_flat`
uses for bindings), and within 2× of the same removal on a local, while every program
still observes exactly the value the copying form would give (tombstones never
visible to any reader).

## Root Cause

`src/codegen/collection/map/map_mutate.rs:lower_map_remove_key_in_place` takes a
`tombstone: bool`. It finds the entry (`emit_map_find_index`), frees the value graph,
flags it `REMOVED` (`emit_map_mark_removed`, which also backward-shift-deletes its
bucket), and then either `emit_map_retire` (tombstone, O(1) amortized) or
`emit_map_compact_from` (the slide).

The field arms always pass `false`:

- `src/codegen/collection/assign/builder_inplace_assign.rs:lower_field_remove_key` —
  `// bug-760 B1: never a tombstone in a field — record copies and comparisons read
  the sub-block without settling it.` → `lower_map_remove_key_in_place(map_slot,
  key_slot, map_type, key_type, false)`.
- `src/codegen/collection/assign/builder_inplace_assign.rs:lower_field_set_remove` —
  the same, `false`.

The binding arms (`try_inplace_remove_key_assign`, `try_inplace_set_remove_assign`)
pass `true`, which `lower_map_remove_key_in_place` ANDs with
`map_key_probe_eligible(key_type)` (`src/codegen/builtins/collections/gen_map.rs`).

`src/codegen/collection/map/map_bucket_remove.rs:lower_map_compact_from_helper`
(`_mfb_rt_map_compact_from`) walks every entry from the removed index to `count`,
copies each survivor five words down, and — when the index is built — re-hashes its key
(`home_slot`: byte-at-a-time FNV + `udiv`) and walks the probe chain to rewrite its
bucket. Removing index 0 moves every entry: O(n) per removal, O(n²) for the loop.

**Why the tombstone was withheld at fields (what makes it unsafe today).** B1 keeps
tombstones invisible with one rule: every read of a `Map`/`Set` *binding* is settled
first. The hook is in `src/codegen/engine/value/builder_values.rs:lower_value`: after
`lower_value_inner`, it calls `emit_map_settle_value` only when the node is
`NirValue::Local | NirValue::Global` **and** the result type is a `Map`/`Set`
(`is_map_or_set_type`), unless the consumer armed `map_settle_exempt_armed`
(`len`/`isEmpty`/`get`/`getOr`/`hasKey`/`contains`). A field's map is not a binding;
it is bytes inlined inside its owner's block (`.ai/collections.md` "Field sites"). It
reaches a consumer by two routes the hook does not cover:

1. **A field path** — `rec.xs`, `f.state.xs`, nested `o.inner.xs`. The
   `NirValue::MemberAccess` arm lowers its base with `lower_value(target)` (a record
   type, not a map, so no settle) and then addresses the member; nothing settles the
   member's sub-block. `keys(rec.xs)`, `FOR EACH x IN rec.xs`, `toString(rec.xs)`,
   `LET m = rec.xs` would read dead entries and a `count` that includes them.
2. **The owner as a whole** — `LET r2 = rec`, `rec = rec2`, `toString(rec)`, a call or
   `RETURN` of `rec`, a thread transfer, `f.state` read whole. These copy or walk the
   owner block with the embedded sub-block verbatim (a flat nested collection is
   inlined by offset and relocated by `memcpy` — `mfb spec memory collections`
   *Collection Layout*), so the copy carries `deadEntries` and the `REMOVED` entries
   into a value whose readers never settle.

The copy itself is harmless — the tombstone state is self-describing (`deadEntries`
lives in the sub-block's own header, `COLLECTION_OFFSET_MAP_STATE` bytes 5..7) — but
no reader downstream of either route is tombstone-aware. That, not anything about the
field layout, is why B1 declined: settling a field is as cheap and as safe as settling
a local (`_mfb_rt_map_settle` compacts in place, never moves or resizes the block, so
the owner's stored offsets and size stay valid), but there was no settle point.

(The other B1 exclusion — key types without a hash probe, whose scan would match a
dead key — is unchanged by this bug and stays excluded.)

## Goal

- G1: `tests/runtime/rt_map_field_fifo_removal_flat.rs` — the probe above as a test:
  for a record field (Map and Set) and a `STATE` field, 20,000 FIFO steps at W and 8W
  (W = 500) take ≤ ×3 at 8W (the `rt_map_fifo_removal_flat` bound), and the surviving

- G2: at W = 500 the field per-step time is ≤ 2× the local's in the same run (today
  38×).
- G3: `map (Record-Fixed) removeKey`, `map (State-Fixed) removeKey`,
  `set (Record-Fixed) remove`, `set (State-Fixed) remove` at -O1 ≤ 2× their plain row
  (plain `map (Fixed) removeKey` 0.017 ms, so ≤ ~0.035 ms), i.e. out of F; the four
  Dynamic field rows fall likewise to ≤ 2× `map (Dynamic) removeKey` /
  `set (Dynamic) remove`.
- G4: tombstones are invisible: every reader of a field-held or owner-copied
  `Map`/`Set` sees exactly the value the copying form gives (the correctness test in
  Phase 1).

### Non-goals (must NOT change)

Owner constraint: no change to the language specification or the memory-management
model.

- **Observable semantics.** A `LET`/argument/`RETURN`/`WITH`/`get` of a record, a
  `STATE` block or a field still behaves as a copy; `removeKey`/`remove` results,
  iteration order (insertion order of the survivors), `len`, equality, `toString`,
  errors and error codes are unchanged. No new syntax, keyword, builtin or signature;
  `mfb man` and `mfb spec language` unchanged.
- **Memory model (`mfb spec memory`).** Copy/mutate/alias rules unchanged; the
  in-place self-update contract (*Self-updates*: failure atomicity, snapshots stay
  snapshots, no per-statement allocation) unchanged; `RES … STATE` semantics
  unchanged (the state block stays the handle's; nothing about open/close/transfer
  changes); the arena allocator and the drop contract unchanged — a tombstone's value
  graph is still freed at the removal, and the owner's graph drop must skip it (as the
  binding drop already does).
- **The block never moves on a read.** Settling stays in place and allocation-free
  (`_mfb_rt_map_settle`'s contract), so no owner offset, `InlineGrow` prefix or
  caller-held sub-block address is invalidated by a settle.
- **Scanned key types keep the slide** (a scan would match a dead key).
- **bug-732's back-removal win** (truncation, no tombstone) must not regress.
- **Forbidden fixes:** changing the benchmark rows (e.g. hoisting `rec.xs` into a
  local), dropping the `LET cur = rec.xs` forwarding, rebuilding the owner, or
  settling at every read of the owner including scalar-field reads (`rec.before`) —
  that would re-introduce an O(n) compaction per iteration in any loop that interleaves
  a removal with a sibling-field read, i.e. the same bug with a different trigger.
- **Cost contract text.** The spec *Cost* sub-bullet that describes the field case as
  "the lookup plus the entries after the removed one" becomes the binding sentence
  ("the lookup plus O(1) amortized"). This is a doc sync that tightens a descriptive
  sub-bullet; the governing cost rule is unchanged. Not a blocker, but it is a spec
  text edit and needs the owner's sign-off (Open Decisions).

## Fix Design

Extend B1's invariant ("only tombstone-aware consumers ever see `dead != 0`") from
bindings to field sub-blocks by adding settle points where a field's map becomes
visible, then let the field arms tombstone.

1. **Member settle.** In the `NirValue::MemberAccess` value path of
   `builder_values.rs:lower_value`, when the member's type is a `Map`/`Set` (or an
   inlined record that transitively inlines one), settle the member's sub-block(s) in
   place with `emit_map_settle_value` — honoring `map_settle_exempt_armed` exactly as
   the binding hook does, so `len(rec.xs)`, `hasKey(rec.xs, k)`, `get(rec.xs, k)`,
   `getOr`, `contains`, `isEmpty` stay tombstone-aware and O(1).
2. **Owner settle, whole-value consumption only.** When a `Local`/`Global` (or the
   `STATE` block) whose record type inlines a `Map`/`Set` is consumed as a whole value
   (copy, compare, `toString`, argument, `RETURN`, transfer), settle each inlined
   map sub-block first (a per-type list of sub-block offsets, computed from
   `record_field_is_inlined` layouts, each a 3-instruction dead-count check when
   clean). The `MemberAccess` arm lowers its base with a "member-base" exemption so a
   scalar field read (`rec.before`) does not settle — see Non-goals.
3. **Field arms tombstone.** Pass `true` in `lower_field_remove_key` /
   `lower_field_set_remove`; flip the `!target.dest.is_field()` gates in
   `builder_inplace_setmap.rs` (difference/symmetricDifference retire; settle-before-walk).
4. **Drop.** Confirm the owner's graph drop reaches an inlined map's entries only
   through the `skip_tombstones` branch; add the skip where it does not.

Why this stays inside `mfb spec memory`: settling is an internal, in-place,
allocation-free normalization that never changes the logical value (*Map Hash Index*,
"Tombstones": "`_mfb_rt_map_settle` … block unmoved"); copies are still copies
(*Operations → Copy*); the removal still frees the removed value's graph at the
removal (plan-134-H); `STATE` stays the handle's block and its field takes the same
route as a record field (`.ai/collections.md`: "The third container is `RES … STATE`").

Where the correctness risk concentrates: a reader that reaches a field sub-block
without either settle point. Mitigation: the B1 approach — a poisoning build that
makes `_mfb_rt_map_settle` a no-op and marks `REMOVED` entries recognizably, run over
the acceptance suite with field removals, plus the Phase 1 invisibility test that
covers every whole-owner consumer listed above.

Rejected alternatives:

- **Keep the slide but skip the re-hash** (one pass over the `2*capacity` buckets
  decrementing every value above `from+1`, or mark the index not-ready). Still O(n) per
  removal: a ~4× constant (guess), not flat — fails G1.
- **Settle on every owner read, including scalar-field reads.** Re-creates the O(n)
  per step for any loop that also reads a sibling field (forbidden in Non-goals).
- **Rebuild the owner / move the map out of the record.** Changes the in-place field
  contract (plan-145) and the layout; forbidden.

Expected output shifts: `.ncode` goldens containing a field `removeKey`/`remove` or a
record read whose type inlines a map (settle call sites). Every delta must be one of:
`_mfb_rt_map_compact_from` → `_mfb_rt_map_retire` at a field arm, or an added settle
check at a member/owner read of a map-inlining record.
