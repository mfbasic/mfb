### 1. "Lives in memory" is not true on macOS (or Windows)
UNIT:      man-page:fs/openData
CLAIM:     "The data lives in memory, not in any directory: no other program can see it, nothing is left behind when the File is closed, and nothing needs cleaning up after a crash." and "Closing it releases the memory."
VERDICT:   wrong
EVIDENCE:  Probe `/tmp/plan-125-scratch/D-phase5-current/man-page-fs-openData/proj_p_backing/src/main.mfb` opens `fs::openData("hello backing", "r")`, sleeps 30 s, then prints `fs::size(f)`. While it slept, `lsof -n -p <pid>` showed fd 4 as a regular file: `REG 1,17 13 /private/var/folders/2n/.../T/mfb-data-b509acd1-a911-4f1b-82bd-410d9d711c06.tmp`; `ls` of that path then reported "No such file or directory" (already unlinked). The source confirms this is by design: the module doc of `src/codegen/builtins/fs/gen_open_data.rs` says only Linux uses `memfd_create`; macOS uses "an exclusive 0600 file in the user temp directory, unlinked as soon as the mode handle is open", and Windows a `FILE_FLAG_DELETE_ON_CLOSE` temp file that keeps its name until closed. So on macOS and Windows the bytes live in a temp file on disk, not in memory, and on Windows the file is visible in the temp directory for the File's whole life (UNVERIFIED here, no Windows host; taken from the module doc). What is true on every platform is the developer-visible contract: no name the program or anyone else can reopen, nothing left behind on close or crash.
SUGGESTED: "The File has no path. Nothing is written to any file you can name, no other program can open it, nothing is left behind when the File is closed, and nothing needs cleaning up after a crash." and, for the second sentence, "Closing it discards the copy."

### 2. Reading a write-only File does not always raise
UNIT:      man-page:fs/openData
CLAIM:     "\"write\" or \"w\" — start empty; value is ignored. The File is write-only: reading raises ErrReadFailed."
VERDICT:   misleading
EVIDENCE:  Probes `proj_p_readw`, `proj_p_readw2`, `proj_p_wseek` under `/tmp/plan-125-scratch/D-phase5-current/man-page-fs-openData/`. On `fs::openData("abc", "w")`: `fs::readAll` printed `s=` (empty string, no error) on the fresh File and again after `writeAll("hello")`; `fs::readAllBytes` returned length 0 with no error; `fs::readLine` and `fs::readBytesAt(f, 0, 3)` raised `77020001 Read operation failed.`; after `fs::seek(f, 0)` with data ahead, `fs::readAll` raised `77020001`. The same `fs::open(path, "w")` disk file also gave `disk readAll=[]`. So `readAll`/`readAllBytes` at the end of the data return empty without touching the handle, and a fresh "w" File is always at its end. A developer who checks "did it raise?" after `readAll` on a "w" File gets a silent empty result, which is the sharp edge the sentence hides. The "append" bullet inherits the same claim ("write-only, as with \"write\"") but there `readAll` did raise (`append readAll err: 77020001`) because the position is 0 with data ahead.
SUGGESTED: "\"write\" or \"w\" — start empty; value is ignored. The File is write-only: fs::readLine, fs::readBytesAt and any read with data ahead of the position raise ErrReadFailed. fs::readAll and fs::readAllBytes return an empty value when the position is already at the end — which it always is on a freshly opened \"w\" File — rather than raising."

Everything else checked out. All three examples were built as projects with `mfb init` + `mfb build` and ran: example 1 printed `alpha` then `beta`; example 2 printed `one`, `two` and a blank line; example 3 printed `3`. Other verified claims, with the probe: write to an "r" File raises `77020002 Write or flush operation failed.` (`proj_p_writer`); "rw" starts at the beginning, overwrites from the current position and grows (`proj_p_rwgrow` printed `Jello world`, `Jello worldXYZ`, `Jello worABCDEF size=15`); "a" keeps the data and appends even after `fs::seek(f, 0)` (`proj_p_append`: sizes 6 then 7); `"R"` and `""` modes raise `77050002 Argument value is not valid` and open nothing (`proj_p_badmode`, `proj_p_badmode2`); the copy is independent in both directions and an empty value gives size 0 with eof TRUE (`proj_p_copy`); `fs::close` on a data File works (`proj_p_eofnl`). `ErrOutOfMemory` is UNVERIFIED: I could not provoke an allocation failure, but the `alloc_error` tail in `gen_open_data.rs:lower_fs_open_data` raises it only on arena allocation failure, matching the page.
