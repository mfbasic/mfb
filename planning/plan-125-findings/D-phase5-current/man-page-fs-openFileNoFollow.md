### 1. The host-mechanism paragraph is written for a kernel engineer, not an MFBASIC developer
UNIT:      man-page:fs/openFileNoFollow
CLAIM:     "The whole-path guarantee is enforced by the host in a single operation. On Linux the path is resolved with openat2 carrying RESOLVE_NO_SYMLINKS; on macOS the open uses O_NOFOLLOW_ANY, which fails if a symlink is encountered at any component. On a Linux kernel too old for openat2 (ENOSYS, pre-5.6, or a restrictive seccomp filter) it falls back to a plain open with O_NOFOLLOW, which refuses only a symlinked final component."
VERDICT:   out-of-scope
EVIDENCE:  `.ai/man-content.md` §1 audience test. Nothing in this paragraph changes what a developer writes except one fact: on an old or seccomp-restricted Linux kernel, only the last path component is checked. The syscall names, flag constants and errno name are host internals. The source comment in `src/codegen/builtins/fs/gen_open.rs` (search `bug-260`) is where that detail belongs and already lives. Also, "in a single operation" is not true on Windows: `lower_fs_open_helper` with `windows_nofollow` opens the file first and then calls `emit_verify_nofollow`, closing the handle and raising ErrAccessDenied if a link or junction was traversed (`gen_open.rs`, search `windows_nofollow`). The page is silent on Windows entirely. UNVERIFIED at run time: no Windows host in the sandbox; read from source only.
SUGGESTED: "The refusal covers every component of the path on macOS, on Windows (where a junction counts as a link), and on Linux 5.6 or newer. On an older Linux kernel, or under a security filter that blocks the newer open call, only a symbolic link at the final name is refused; a link at an intermediate directory is followed silently there."

### 2. "readWrite" writes land at the start of the file, overwriting what is there
UNIT:      man-page:fs/openFileNoFollow
CLAIM:     "\"readWrite\" opens the file for both reading and writing, creating it when it does not exist but preserving existing contents."
VERDICT:   incomplete
EVIDENCE:  Probe `p1/src/main.mfb`: wrote "abcdef", opened with "rw", `fs::writeAll(rw, "ZZ")`, closed, read back. Output: `after rw open+write ZZ: [ZZcdef]`. The contents are preserved at open, but the first write starts at position 0 and overwrites, which a reader contrasting "rw" with "append" in the same sentence pair is likely to miss. The same probe shows "a" writes at the end: `after a open+write !: [ZZcdef!]`.
SUGGESTED: "\"readWrite\" opens the file for both reading and writing, creating it when it does not exist and keeping existing contents; reads and writes start at the beginning of the file, so a write overwrites what is there unless you fs::seek first. Use \"append\" to add at the end."

### 3. A link whose target does not exist is reported as a link, not as a missing file
UNIT:      man-page:fs/openFileNoFollow
CLAIM:     "ErrAccessDenied if a component of path is a symbolic link or permission is refused, ErrPathNotFound if the file does not exist"
VERDICT:   incomplete
EVIDENCE:  Probe `p2/src/main.mfb` with `fx/dangling -> nowhere.txt`: `dangling link read -> code 77030003` and `dangling link write -> code 77030003` (ErrAccessDenied), not ErrPathNotFound, in both read and create modes. The page's two clauses leave it ambiguous which wins when both apply.
SUGGESTED: Append to the ErrAccessDenied clause: "a symbolic link is refused before its target is looked at, so a link pointing at a missing file raises ErrAccessDenied, not ErrPathNotFound."
