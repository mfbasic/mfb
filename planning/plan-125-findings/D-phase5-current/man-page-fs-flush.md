### 1. Example caption says "to disk"; `flush` only hands bytes to the operating system
UNIT:      man-page:fs/flush
CLAIM:     "Force buffered data to disk at a checkpoint, then keep writing."
VERDICT:   misleading
EVIDENCE:  `src/codegen/builtins/fs/gen_handle.rs:lower_fs_file_drain` issues only `platform.emit_write` in a loop; `grep -rn fsync src/codegen/builtins/fs/` hits only `gen_atomic_write/`, never `gen_handle.rs`. The intro and description correctly say "to the file"; only the example caption promises disk durability, which `fs::writeTextAtomic`/`fs::writeBytesAtomic` provide and `fs::flush` does not.
SUGGESTED: "Force buffered data out to the file at a checkpoint, then keep writing." (and, if the page wants to state the edge: "`fs::flush` hands the bytes to the operating system; it does not wait for them to reach storage.")

### 2. Flushing a closed `File` is a build error in the common case, not a runtime one
UNIT:      man-page:fs/flush
CLAIM:     "Flushing a `File` that has been closed raises `ErrResourceClosed`, and flushing one handed to another thread with `thread::transfer` raises `ErrResourceMoved`."
VERDICT:   incomplete
EVIDENCE:  Probe p2 (`RES out = fs::openFile(p,"write")` / `fs::close(out)` / `fs::flush(out)`) does not build: `error[2-203-0055 TYPE_USE_AFTER_MOVE]: binding is used after move`. Probe p3 (record `Holder` with `handle AS RES fs::File`, copy `b` of `a`, `shut(a)` closes it, then `fs::flush(b.handle) TRAP(e)`) prints `flush through the other copy: TRUE` for `e.code = errorCode::ErrResourceClosed`. The sibling `fs::close` page (commit eca9367e7) already states both halves; this page states only the runtime half. For the `ErrResourceMoved` half: UNVERIFIED by probe (no thread probe run); `gen_handle.rs:emit_closed_guard` → `resource::closed_or_moved_guard` raises it, and `mfb man thread transfer` says "on success you cannot use it again", so the same two-halves wording applies.
SUGGESTED: "In the function that closed or transferred it, the compiler rejects naming the `File` again (build error `TYPE_USE_AFTER_MOVE`). A closed `File` reached another way — through a second copy of a record that holds it, after a function it was passed to closed it — raises `ErrResourceClosed`; one that `thread::transfer` has handed to another thread raises `ErrResourceMoved`."

Everything else on the page held under probe. Example `ex.mfb` built and printed `id,name` then a blank line (`io::print` of the header). Probe p1 printed `before flush: []`, `after flush: [pending]`, `before scope exit: [pending]`, `after scope exit: [pending tail]` (scope-exit close drains), `buffered by default? FALSE`, unbuffered write visible before and after flush (no-op), repeated flushes with no pending bytes fine, and `fs::flush` on a read-mode handle succeeds. Probe p4 printed `p after flush(a): [A] q: [] b buffered: TRUE`, confirming flush is per handle. The partial-write and `ErrWriteFailed` retry claims are UNVERIFIED by probe (no way to force a short `write` here) but match `lower_fs_file_drain`'s loop and the bug-311 slide-back-on-error path. No banned vocabulary or compiler-model sentences found on the page.
