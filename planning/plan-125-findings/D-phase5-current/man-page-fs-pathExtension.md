### 1. `.` and `..` components yield `"."`, not an empty String
UNIT:      man-page:fs/pathExtension
CLAIM:     "The operation is purely syntactic: it inspects the bytes of `path` and never consults the filesystem, resolves `.` or `..` segments, follows symbolic links, or checks whether any path exists." together with "When the final component contains no `.`, an empty `String` is returned."
VERDICT:   incomplete
EVIDENCE:  Probe under /tmp/plan-125-scratch/D-phase5-current/man-page-fs-pathExtension/probe (built with the release `mfb build`, run `./probe/build/mfb_project.out`): `"."` → `[.]`, `".."` → `[.]`, `"dir/.."` → `[.]`, `"dir/."` → `[.]`, `"note."` → `[.]`. The scan in `gen_path_builder.rs:fs_path_extension_window` stops at the last byte 46 wherever it is, so a bare `.`/`..` component and a name ending in `.` all return a one-byte `"."`. The page covers "no `.`" and "only `.` is the first byte" but says nothing about a final component that *is* a dot component or *ends* in a dot, which is the case a developer walking a directory listing hits immediately (`.` and `..` entries). Nothing on the page lets a reader predict `[.]`.
SUGGESTED: Add after the dotfile sentence: "A component that ends in `.` yields `"."`: `"note."`, `"."`, `".."` and `"dir/.."` all return `"."`, because the scan stops at the last `.` and the result runs from there to the end of the component. Test for `"."` yourself if you need to treat these as having no extension."

### 2. `\` is not a separator — Windows-style paths cross components
UNIT:      man-page:fs/pathExtension
CLAIM:     "The scan is byte-oriented (the separator is the single byte `47` and the dot is the single byte `46`), so UTF-8 file names are preserved unchanged and any embedded bytes are treated literally."
VERDICT:   incomplete
EVIDENCE:  Same probe: `"dir.d\file"` → `[.d\file]`, `"C:\x.d\README"` → `[.d\README]`. The lowering compares only against byte 47 (`compare_immediate(&byte, "47")` in `fs_path_extension_window`). The page states the fact numerically ("byte 47") but never states its consequence, which is the sharp edge: a backslash is an ordinary name byte, so a `.` in an earlier backslash-separated component is returned as part of the "extension". A developer handling Windows paths cannot infer that from "the separator is byte 47" without decoding ASCII in their head.
SUGGESTED: Replace the parenthetical with plain words: "The scan is byte-oriented and the only separator is `/`. A backslash is an ordinary name byte, so `"dir.d\file"` yields `".d\file"`, not an empty String. UTF-8 file names are preserved unchanged: `"dir/fïlé.tést"` yields `".tést"`."

Everything else on the page was verified true. The five examples compiled and printed `.txt`, `.gz`, an empty line, an empty line, `.bashrc`, matching the page. The probe confirmed: trailing `/` and `///` trimmed (`.txt`), empty path and `"///"` give an empty String, `"dir/.bashrc"` gives `.bashrc`, `".bashrc.bak"` gives `.bak`, `"dir/日本.ファイル"` gives `.ファイル`, and a `MUT` argument is unchanged afterwards (`keep/me.txt`), so the "new String" claim is a copy, not a mutation. The Errors table (only `ErrOutOfMemory`) matches the descriptor's `errors: vec!["ErrOutOfMemory"]` in `func_path_extension.rs`, and the lowering makes no other raise. No banned memory vocabulary and no compiler-internal terms appear on the rendered page.
