### 1. Symlink loop is ErrInvalidPath, not the "any other refusal" ErrWriteFailed
UNIT:      man-page:fs/appendText
CLAIM:     "and ErrInvalidPath if path cannot name a file — it names a directory, a name in it is too long, or a file is used as a directory. Any other refusal, and a failed write, flush to disk or close, raises ErrWriteFailed."
VERDICT:   incomplete
EVIDENCE:  `src/codegen/builtins/fs/gen_shared.rs:emit_fs_host_error_mapping` maps `ELOOP` (62 macOS / 40 Linux) to `invalid_path` when `no_follow` is false, which is the flag `lower_fs_write_path_helper` passes. Probe `/tmp/plan-125-scratch/D-phase5-current/man-page-fs-appendText/p_err.mfb` with fixtures `loop1 -> loop2 -> loop1` printed `symlink-loop: Filesystem path string is invalid for the host platform.` (the ErrInvalidPath message). A reader following the page's enumerated list and its "Any other refusal → ErrWriteFailed" catch-all would expect ErrWriteFailed here. The same mapping also sends an invalid-name encoding (`EILSEQ`) to ErrInvalidPath, which the page does not mention either.
SUGGESTED: "...and ErrInvalidPath if path cannot name a file — it names a directory, a name in it is too long, a file is used as a directory, a symlink chain in it loops, or the host filesystem rejects the name. Any other refusal, and a failed write, flush to disk or close, raises ErrWriteFailed."

### 2. The NUL rule is justified by the host C call, not by the language
UNIT:      man-page:fs/appendText
CLAIM:     "The string must not be empty and must not contain an embedded NUL byte, because the host open call requires a NUL-terminated path."
VERDICT:   out-of-scope
EVIDENCE:  The rule itself is true: `lower_fs_write_path_helper` branches to `invalid` on `len0 == 0` and `emit_cstring_copy(..., true, ...)` branches to `invalid` on a NUL byte; probes printed `empty: Argument value is not valid...` and `nul: Argument value is not valid...` (`p_err.mfb`, `p_nul.mfb`). But the clause after "because" explains the implementation's C-string convention (`.ai/man-content.md` §1/§3: a sentence that only matters to someone reading the lowering). The developer needs the rule and the error, which the last paragraph already gives; the reason belongs in `mfb spec`.
SUGGESTED: "The string must not be empty and must not contain a NUL byte; either raises ErrInvalidArgument before the file is touched."
