### 1. Use after close or transfer is usually a build error, not a runtime raise
UNIT:      man-page:fs/isBuffered
CLAIM:     "Calling it on a `File` that has been closed raises `ErrResourceClosed`, and on one handed to another thread with `thread::transfer`, `ErrResourceMoved`."
VERDICT:   misleading
EVIDENCE:  Naming the binding after `fs::close(r)` or `thread::transfer(t, f, 2000)` in the same function does not compile: `mfb build` on /tmp/plan-125-scratch/D-phase5-current/man-page-fs-isBuffered/proj_p1 (first draft) and proj_p3 (first draft) both reported `error[2-203-0055 TYPE_USE_AFTER_MOVE]: Binding `r` was moved and cannot be used again` / `Binding `f` was moved`. The runtime raises are reachable only when the close or transfer happens where the compiler cannot see it. proj_p2 (helper `closeIf(w, TRUE)` then `fs::isBuffered(w) TRAP(err)`) printed `closed raised: 77030004`; proj_p3 (helper `sendIf(t, f, TRUE)` then `fs::isBuffered(f) TRAP(err)`) printed `sender after raised: 77030009`. Commit eca9367e7 fixed exactly this sentence on `fs::close`, the `fs` overview and `canvas::destroyFont`/`destroyImage` ("the pages now state both halves"); this page was left with the old one-half wording.
SUGGESTED: "A closed or transferred `File` is never queried again. Naming the binding after `fs::close` or `thread::transfer` in the same function is the build error `TYPE_USE_AFTER_MOVE`; a use the compiler cannot see — through a callee that closed it, or another copy of a record that holds it — raises `ErrResourceClosed` after a close and `ErrResourceMoved` after a `thread::transfer`."

### 2. The transfer reset discards pending buffered bytes, and the page does not say so
UNIT:      man-page:fs/isBuffered
CLAIM:     "Transferring a buffered handle to another thread resets it to unbuffered, so the receiving thread again observes `FALSE`."
VERDICT:   incomplete
EVIDENCE:  proj_p3: `fs::setBuffered(f, TRUE)`, `fs::writeAll(f, "pending-before-transfer\n")`, transfer to a worker that does `fs::writeAll(f, "worker\n")` and closes, then `fs::readText(path)` printed `file content: [worker\n]`. The sender's pending bytes were lost. The "observes FALSE" half is verified (`worker saw: FALSE`), but the sharp edge the reader needs — the reset drops whatever was not flushed — is stated only on the `fs::setBuffered` page ("should also be flushed before it is transferred"). `src/codegen/builtins/fs/mod.rs` `RegistryResource` for `File` (`live_slots: &[]`, comment "a move intentionally RESETS") confirms it is by design, not a bug in the probe. If the main thread judges silent loss on transfer to be a defect rather than a contract, that is an `fs`/`thread::transfer` bug to file; the page must say one or the other.
SUGGESTED: "Transferring a buffered handle to another thread resets it to unbuffered and discards any bytes still held in its buffer, so flush it first; the receiving thread observes `FALSE`."

Everything else on the page checked out. The example built as a project and printed `TRUE`, exit 0. proj_p1 printed `default write: FALSE`, `after TRUE: TRUE`, `other handle: FALSE` (a second open File is unaffected), `after FALSE: FALSE`, `default read: FALSE`, matching the default, toggle and per-handle claims and the lowering in `gen_handle.rs:lower_fs_is_buffered_helper` (closed guard, then a load of `FILE_OFFSET_BUF_ENABLED` compared with zero, no writes). Error codes 77030004 and 77030009 match the rendered Errors table. A whole-word sweep of the rendered page for the §4 banned list returned no hits, and no sentence teaches a borrow or ownership model without the words.
