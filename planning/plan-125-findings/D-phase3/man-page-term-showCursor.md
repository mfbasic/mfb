### 1. A macOS `--app` build never draws the cursor, so the visibility change the page promises does not happen there
UNIT:      man-page:term/showCursor
CLAIM:     "In a terminal program, and in a macOS --app build, the cursor's visibility changes when term::sync presents the next frame; a Linux --app build repaints from this call itself."
VERDICT:   wrong
EVIDENCE:  The macOS app body stores the flag and nothing ever reads it back for drawing. `grep -rn TV_CURSOR_VISIBLE_OFFSET src/target/macos_aarch64/` returns exactly three hits: the constant (`app/mod.rs:519`), the `term::on` initial store (`app/term_view.rs:1199`), and the `showCursor`/`hideCursor` store (`app/app_io.rs:emit_app_set_cursor_visible`, whose own doc comment reads "Cursor glyph rendering is a later refinement, so no redraw is needed yet"). There is no load in the view's paint path, and `grep -n -i caret src/target/macos_aarch64/` is empty. The same holds for a Windows `--app` build: `grep -n CURSOR_VISIBLE src/target/win_x86_64/app/mod.rs` shows only the `term::on` reset store (line 3711) and the setter store (`emit_term_cursor_visible`), no read in the paint. Only two backends honour the flag: the terminal program, whose present emits `\x1b[?25h`/`?25l` from the flag (`src/codegen/term/grid/term_grid.rs` present routine, the block after "Reset SGR, restore cursor position + visibility"), and the Linux `--app` build, which draws a caret when the flag is set (`src/target/linux_gtk/term_draw.rs:687-709`) and queues a redraw from the call (`app_io.rs:emit_app_term_set_cursor`, `g_idle_add`). Terminal-program behaviour confirmed by running the page's example under `script`: the first present ends `ESC[2;1H ESC[?25l`, the second ends `ESC[3;7H ESC[?25h`. I could not observe an `--app` window from the sandbox; the macOS/Windows verdict rests on the absence of any read of the flag in the drawing code.
SUGGESTED: "The change is not shown straight away. In a terminal program the cursor's visibility changes when term::sync presents the next frame; a Linux --app build repaints from this call itself. A macOS or Windows --app build accepts the call and remembers the setting, but draws no cursor at all, so it has no visible effect there. Each present leaves the terminal cursor at the position the next drawing would use, so a visible cursor always tracks that position."

### 2. The page names macOS and Linux app builds but is silent on Windows
UNIT:      man-page:term/showCursor
CLAIM:     "In a terminal program, and in a macOS --app build, the cursor's visibility changes when term::sync presents the next frame; a Linux --app build repaints from this call itself."
VERDICT:   incomplete
EVIDENCE:  `term.showCursor` is on the Windows console routing list (`src/target/win_x86_64/mod.rs:85`, the "Phase D — term styling / TUI" block), so a Windows terminal program takes the shared present path and does honour the flag; a Windows `--app` build does not (see finding 1). A developer reading this sentence cannot tell which of the two Windows cases applies. Folded into the wording in finding 1.
SUGGESTED: Use the wording in finding 1, which names all four cases.

Verified and left alone, for the audit trail: the inactive gate ("while TUI mode is off it does nothing and reports no error") was probed with a program calling `term::showCursor()` three times before any `term::on`; it printed only `isOn=false` and `done`, no escape bytes, exit 0 (`emit_set_cursor_visible` → `emit_gate_inactive`). The `term::on` reset to visible is the store of `1` at `TERM_STATE_CURSOR_VISIBLE_OFFSET` in `emit_on` (`src/codegen/term/core/term.rs`, "Reset all state to defaults"). The example compiled with `mfb build` and ran under a pty with the sequence described in finding 1. No banned vocabulary and no borrow-model sentence on the page.
