### 1. Wide glyphs advance the cursor two columns, not one
UNIT:      man-page:term/moveTo
CLAIM:     "Drawing advances the cursor on its own: each glyph moves it one column right, wrapping to column 0 of the next row at the right edge and scrolling the surface up by one row at the bottom."
VERDICT:   wrong
EVIDENCE:  Probe `/tmp/plan-125-scratch/D-phase3/man-page-term-moveTo/clamp.bas` run in a 10x20 pty via `script -q ... sh -c "stty rows 10 cols 20; ./clampp.out"`: after `term::moveTo(1, 0)` then `io::write("漢C")`, the presented frame is `^[[2;1H…漢C…` and the final cursor placement is `^[[2;4H`, i.e. zero-based (1, 3) after two glyphs — 漢 took two cells. Source: `src/codegen/term/grid/term_grid.rs` `emit_grid_write`, `abi::add_registers(col, col, width)` with `width` 1 or 2, and the comment "A width-2 glyph at the last column wraps rather than straddling the edge." The wrap and scroll halves of the sentence are correct (`emit_scroll_back` at both the wrap and `\n` paths).
SUGGESTED: "Drawing advances the cursor on its own: each glyph moves it right by the number of cells it occupies — one for most characters, two for an East Asian wide character — wrapping to column 0 of the next row at the right edge (a wide glyph that would not fit in the last column wraps whole) and scrolling the surface up by one row at the bottom."

### 2. The clamp bound is the surface's dimensions, which lag `term::terminalSize` until the next `term::sync`
UNIT:      man-page:term/moveTo
CLAIM:     "…a value at or past the edge becomes the last valid cell — rows-1 for the row, columns-1 for the column, using the current surface dimensions that term::terminalSize reports."
VERDICT:   misleading
EVIDENCE:  `src/codegen/term/core/term.rs` `emit_move_to` loads `rows`/`cols` from the grid header (`load_u64("%v10", "%v9", 0)` / `("%v11", "%v9", 8)`), whereas `emit_terminal_size` in the same file issues a live `TIOCGWINSZ` ioctl and never touches the grid. The grid header is only re-read on `term::on` and at `term::sync` entry (`src/codegen/term/grid/term_grid.rs` `emit_grid_resize`: "Detect a terminal resize at `term::sync` entry and reflow the grid"). So after the user resizes the window and before the program's next `term::sync`, `term::terminalSize` reports the new size while `term::moveTo` clamps to the old one. Console backend verified by source; I did not run a mid-run pty resize probe (UNVERIFIED by execution, verified by reading the three emitters).
SUGGESTED: "…using the surface's current dimensions. The surface takes its size from the terminal at term::on and again at each term::sync; between a window resize and the next term::sync, term::terminalSize already reports the new size while the clamp still uses the old one."

### 3. In an app build outside Console mode the call raises, but the page (and its Errors table) says it never reports an error
UNIT:      man-page:term/moveTo
CLAIM:     "The call is gated: while TUI mode is off it does nothing and reports no error."
VERDICT:   incomplete
EVIDENCE:  `src/codegen/builtins/term/gen_shared.rs` `lower_term_helper`: in an `--app` build every `term::` helper is wrapped by `prepend_wrong_mode_gate(…, ModeRequirement::Console)`, raising the trappable `ErrWrongMode` when the program is in `app::Mode.None` or `Mode.Canvas`. The spec confirms it (`src/docs/spec/diagnostics/02_error-codes.md`, row `ErrWrongMode`: "In an `--app` build, `term::*` requires `app::Mode.Console` … so `None` and `Canvas` both trap"). The descriptor's `errors: vec![]` in `func_move_to.rs` therefore leaves the derived Errors table empty, while the `canvas` package's descriptors (e.g. `src/codegen/builtins/canvas/func_present.rs`) do declare `ErrWrongMode`. This gap is package-wide across all `term` pages, not unique to `moveTo`; the page's TUI-off sentence is true on the console backend (probe `clamp.bas`: the pre-`term::on` `moveTo(5, 5)` printed nothing and exit status was 0).
SUGGESTED: Keep the sentence and add: "In a program built with `--app`, the call additionally requires `app::Mode.Console`; in `Mode.None` or `Mode.Canvas` it raises `ErrWrongMode`." And add `ErrWrongMode` to the descriptor's `errors` (a descriptor fix, so the derived table shows it), as the canvas package already does.

Everything else on the page checked out. Probe results, all from `/tmp/plan-125-scratch/D-phase3/man-page-term-moveTo` built with `mfb build -q` and run in a 10x20 pty under `script`: both page examples compile and run; example 1 draws `top-left` at `^[[1;1H`; example 2 draws `middle` at row 6, column 11 (zero-based (5, 10) = rows/2, columns/2); `moveTo(-7, -7)` lands `A` at (0, 0); `moveTo(99999, 99999)` lands `B` at the last cell (row 10, column 20); no error is raised for either. `\n`, `\r`, `io::print`'s trailing newline and `term::clear` homing to (0, 0) are as described (`term_grid.rs` `handle_nl`/`handle_cr`/`append_newline`; `term.rs` `emit_clear_grid` stores 0 to header offsets 16 and 24). `emit_move_to` stores only the two cursor words, so "draws nothing, erases nothing, and leaves the colours and attributes alone" holds, and the move emits no terminal bytes until `sync`. Clamping is present on the macOS, Linux GTK and Windows app backends as well as the console backend. No banned memory vocabulary and no compiler-internal sentences on the page.
