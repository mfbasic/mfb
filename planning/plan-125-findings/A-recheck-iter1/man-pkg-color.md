### 1. Overview describes a third of the package and omits the theme every adjustment page leans on
UNIT:      man-pkg:color
PAGE:      package-wide (overview `Description`)
CATEGORY:  overview-mismatch
CLAIM:     "One colour type for the whole language: an 8-bit-per-channel RGBA value with constructors, a packed-integer bridge, and hex text forms." and "The color package defines color::Color, the colour value every other package speaks."
VERDICT:   misleading
EVIDENCE:  `sed -n 105,153p src/codegen/builtins/color/mod.rs | grep -oE "color::[A-Za-z]+" | sort -u` names 11 members (Color, fromHex, fromName, fromPacked, gray, green, rgb, rgba, toHex, toHexAlpha, toPacked); `ls src/codegen/builtins/color/func_*.rs | wc -l` is 28. The same range grepped for `hsl|linear|luminance|contrast|brighten|darken|mix|saturate|rotateHue|isDark|withAlpha|invert|Hsl` returns 0. Yet the rendered pages for brighten, darken, hsl, hsla, toHsl, saturate, desaturate, rotateHue, toLinear and the `Hsl` record all repeat the same "HSL describes the sRGB colour, brighten/darken/mix work in linear light, the two deliberately disagree" rule (`mfb man color --all`, saved at /tmp/plan-125-scratch/A-recheck-iter1/man-pkg-color/all.txt). The overview also says the package defines one type; `mfb man color types` lists two records, `color::Color` and `color::Hsl`. A developer who arrives asking "how do I lighten / blend / check contrast / get a complementary colour" reads the overview and finds no sentence saying the package does any of that; the only route is scanning a 28-row alphabetical table where "brighten" and "hsl" sit far apart from the rule that relates them.
SUGGESTED: Keep the existing paragraphs and add one short section after the hex paragraph, roughly: "Beyond building and spelling colours, the package adjusts them in three families. Hue-based adjustments — color::hsl / color::hsla / color::toHsl (returning a color::Hsl), color::saturate, color::desaturate, color::rotateHue — work in the HSL model on the sRGB colour, the same numbers CSS hsl() and design tools show. Light-based adjustments — color::brighten, color::darken, color::mix, color::grayscale, built on color::toLinear / color::fromLinear — work in linear light so a fraction is a fraction of real light. The two spaces deliberately disagree: a lightness bump in one is not a brighten in the other. The accessibility members — color::luminance, color::contrastRatio, color::isDark, color::isLight — answer 'can this be read against that' using the WCAG definitions. color::invert and color::withAlpha are channel operations." Also change the intro to mention adjustment and accessibility, and "defines color::Color" to "defines color::Color and the color::Hsl view of it".

### 2. No page says how to flatten a translucent colour onto its background, though two pages tell the developer they must
UNIT:      man-pkg:color
PAGE:      color::contrastRatio (also color::isDark, color::luminance, overview)
CATEGORY:  coverage
CLAIM:     "A contrast ratio involving a transparent colour is not meaningful until you know what it is drawn over, so measure the colour that actually ends up on screen. color::mix does not produce that: it blends two colours and their alpha, rather than laying one over the other."
VERDICT:   missing
EVIDENCE:  `grep -il "over\b\|composite\|flatten" src/codegen/builtins/color/func_*.rs` finds no member and no page describing the over operation; the contrastRatio page names what will not do it and stops. The operation is expressible with existing members and matches what canvas does: `src/codegen/builtins/canvas/helper_color.rs:__canvas_blendChannel` is `dstLin + (srcLin - dstLin) * alpha / 255` through `color::toLinear`/`color::fromLinear`, i.e. a linear-light lerp by alpha/255 onto the destination. Probe /tmp/plan-125-scratch/A-recheck-iter1/man-pkg-color/p4 built with `mfb build -q .` and run: `color::mix(bg, color::withAlpha(fg, 255), toFloat(toInt(fg.alpha)) / 255.0)` for fg = rgba(255,0,0,128) over white printed `#ffbbbbff`; contrastRatio of that flattened colour against white printed `1.61`, while contrastRatio of the raw translucent fg against white printed `4.00`. The naive call passes body-text contrast; the real on-screen colour fails it. That is exactly the trap the page warns about, with no way out offered.
SUGGESTED: On contrastRatio, after "measure the colour that actually ends up on screen", add: "For a translucent foreground over an opaque background, that colour is `color::mix(bg, color::withAlpha(fg, 255), toFloat(toInt(fg.alpha)) / 255.0)` — a linear-light blend by coverage with the alpha forced opaque, which is the same over operation canvas draws with." Mention the same recipe on `mix` (as the one use of `withAlpha` with it) so See also picks it up.

### 3. rotateHue and withAlpha are dead ends: neither page links to any sibling
UNIT:      man-pkg:color
PAGE:      color::rotateHue, color::withAlpha
CATEGORY:  discoverability
CLAIM:     Both pages render with no `See also` section.
VERDICT:   missing
EVIDENCE:  `awk` over the rendered `mfb man color --all` output for page headings not followed by a "See also" heading lists exactly ROTATEHUE, WITHALPHA and TYPES (/tmp/plan-125-scratch/A-recheck-iter1/man-pkg-color/all.txt). Per `.ai/man-content.md` §0, See also is derived from the `color::name` references in `desc`; `src/codegen/builtins/color/func_rotate_hue.rs` and `func_with_alpha.rs` DESC name no sibling. rotateHue says "Hue is an HSL property" without naming `color::toHsl`, `color::hsl` or `color::saturate`, and says a grey "has no hue to turn" while the saturate page spends two paragraphs on the opposite behaviour for the same grey — the two pages never point at each other. withAlpha is linked from rgb, rgba, brighten and the proposed over recipe, but links back to none; a developer reading it cannot reach `color::rgba` (the other way to set alpha) or `color::hsla`.
SUGGESTED: rotateHue desc: "Hue is an HSL property (color::toHsl reports it, color::hsl builds from it), so this works on the sRGB colour … A grey … returns it unchanged — unlike color::saturate, which turns a grey red." withAlpha desc: "It is the alpha-only counterpart of building the colour afresh with color::rgba or color::hsla; color::brighten, color::darken and the HSL adjustments all leave alpha alone, so this is the one member that changes it."

Checked and found consistent across pages, so not reported: the desaturate/grayscale disagreement (probe printed `#808080` vs `#4c4c4c` for blue), saturate-on-grey turning red (`#ff0101`) versus rotateHue-on-grey unchanged (`#808080`), the mix midpoint `#bcbcbc`, gray(128) luminance `0.22` and darken(white, 0.5) landing on `188`, the brighten/darken non-inverse `#8b91aa`, the CSS green constant matching `fromName("green")`, and the overview's claims that `color::gray` reads as both constant and function, that `color::Color[...]` works and rejects 300 at compile time (`TYPE_BYTE_LITERAL_OVERFLOW`), that prefix `WITH` updates work, that `=` compares colours, and that `toString` renders `#rrggbbaa` (probes p1–p3 under /tmp/plan-125-scratch/A-recheck-iter1/man-pkg-color).
