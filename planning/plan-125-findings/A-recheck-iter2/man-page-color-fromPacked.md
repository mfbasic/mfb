### 1. The page is about `0xAARRGGBB` but every constant in it is decimal
UNIT:      man-page:color/fromPacked
CLAIM:     "Add the alpha before unpacking (color::fromPacked(bits::bor(rgb24, 4278190080)))" and, in the examples, "LET c AS color::Color = color::fromPacked(4281558732)" / "LET rgb24 AS Integer = 3368652        ' 0x3366CC" / "bits::bor(rgb24, 4278190080)"
VERDICT:   misleading
EVIDENCE:  The language has hex integer literals: `mfb spec language lexical-structure` line 66, "Radix prefixes. A literal may begin with a base prefix — 0x/0X (hexadecimal) … 0xFFF is 4095". Verified against the binary: /tmp/plan-125-scratch/A-recheck-iter2/man-page-color-fromPacked/hex/src/main.mfb uses `color::fromPacked(0xFF3366CC)`, `LET rgb24 AS Integer = 0x3366CC` and `bits::bor(rgb24, 0xFF000000)`; `mfb build .` succeeded and the binary printed `51 102 204 255` and `0 vs 255`, byte-identical to the decimal-constant examples (ex1/ex2, same directory, same output). A page whose intro, description and parameter column all speak in `0xAARRGGBB` and then writes `4281558732` with a comment translating it back to hex teaches the reader that hex cannot be written in source, which is false, and makes the alpha mask `4278190080` opaque where `0xFF000000` is self-describing.
SUGGESTED: In the description: "Add the alpha before unpacking (`color::fromPacked(bits::bor(rgb24, 0xFF000000))`), or use `color::fromHex` …". Example 1: drop the translating comment and write `LET c AS color::Color = color::fromPacked(0xFF3366CC)   ' red 0x33, green 0x66, blue 0xCC, alpha 0xFF`. Example 2: `LET rgb24 AS Integer = 0x3366CC` and `color::fromPacked(bits::bor(rgb24, 0xFF000000))`. (All three variants compiled and ran as above.)

### 2. "exact inverse" holds in one direction only
UNIT:      man-page:color/fromPacked
CLAIM:     "fromPacked is the exact inverse of color::toPacked"
VERDICT:   misleading
EVIDENCE:  `fromPacked(toPacked(c)) == c` holds (probe `roundtrip: 10 20 30 40` from /tmp/plan-125-scratch/A-recheck-iter2/man-page-color-fromPacked/probe/src/main.mfb), but `toPacked(fromPacked(v)) == v` does not: the same probe printed `neg1: 255 255 255 255` and `packed(-1 colour)=4294967295`, i.e. `-1` goes in and `4294967295` comes back, and `high32`/`high40` (the opaque value plus bit 32, plus bit 40) both print `51 102 204 255`, collapsing to `4281558732`. Implementation: `src/codegen/builtins/color/func_from_packed.rs:BODY` masks each shifted channel with `bits::band(…, 255)`; `func_to_packed.rs:__color_toPacked` only ever produces `0..4294967295`. The next paragraph's "Only the low 32 bits of value are read" is the real contract; "exact inverse" overstates it for a reader who tries to round-trip an Integer rather than a Color.
SUGGESTED: "fromPacked undoes color::toPacked: it reads alpha from the highest of the low four bytes, then red, then green, then blue — 0xAARRGGBB — and returns the colour they describe, so fromPacked(toPacked(c)) is always c. Going the other way, toPacked(fromPacked(v)) equals v only when v is in 0..4294967295 (0x00000000..0xFFFFFFFF); see the next paragraph."

Everything else on the page checked out against the binary. Both rendered examples compiled with `mfb build .` and printed `51 102 204 255` and `0 vs 255`, matching the comment and the "fully transparent … 255" claim. The probe confirmed `fromPacked(0)` is `0 0 0 0`, a negative value with a non-trivial low word (`-9223372036854775808 + 0x0A141E28`) unpacks to `20 30 40 10` (red green blue alpha), and the minimum Integer unpacks to all zeros, so "Anything above them is ignored, so a value that arrived with high bits set, or a negative one, still yields a colour rather than failing" is true. The Errors table is empty and the descriptor's `errors: vec![]` and body (`toByte` of a masked 0..255 value) can raise nothing. The page has no Errors rows to check, no `RES` handle, and the full `scripts/man-census.sh --banned-list` pattern grepped against the rendered page returned no hits (grep exit 1); no sentence teaches an ownership model without a banned word.
