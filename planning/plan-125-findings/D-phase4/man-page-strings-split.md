### 1. Round-trip example does not round-trip
UNIT:      man-page:strings/split
CLAIM:     "Split and rejoin to round-trip the value:" (caption of the third example, which calls `strings::join(parts, "-")` on the pieces of `"a😀b😀c"` split on `"😀"`)
VERDICT:   misleading
EVIDENCE:  Built and ran the example verbatim (`/tmp/plan-125-scratch/D-phase4/man-page-strings-split/proj_ex3`, `mfb build .` then `./build/proj_ex3.out`). Output: `a-b-c`. The original value was `a😀b😀c`, so the example demonstrates split-then-join-with-a-different-delimiter, not a round trip. The description two paragraphs earlier defines the round trip as "Joining the result with the same non-empty delimiter reproduces value exactly". A reader who copies this example to check that sentence sees it apparently fail. My probe confirms the real round trip does hold: `strings::join(strings::split(",a,,b,", ","), ",") = ",a,,b,"` printed `roundtrip=TRUE`.
SUGGESTED: Either change the caption to "Split on a multi-byte delimiter and rejoin with a different one:" or make the example an actual round trip, e.g. `io::print(toString(strings::join(parts, "😀") = "a😀b😀c"))` printing `TRUE`. Keeping a multi-byte delimiter in the example is worth preserving, since it is the page's only demonstration of the "never lands mid-scalar" claim.

### 2. "inverses" is only true in one direction
UNIT:      man-page:strings/split
CLAIM:     "Joining the result with the same non-empty delimiter reproduces value exactly — split and strings::join are inverses."
VERDICT:   misleading
EVIDENCE:  The first half of the sentence is verified (probe printed `roundtrip=TRUE` for `",a,,b,"`). The second half overstates it: the reverse composition split(join(xs, d), d) does not reproduce xs whenever an element already contains d. From the probe's `basic` line, `strings::split("a,b,c", ",")` yields 3 elements, and `"a,b,c"` is exactly what `strings::join(["a,b", "c"], ",")` produces (join concatenates bytes verbatim per `mfb man strings join`), so a 2-element list comes back as 3. The join page states the claim correctly and one-directionally ("joining the result of split(value, delimiter) with the same delimiter reproduces value"); this page's trailing clause drops that qualification.
SUGGESTED: "Joining the result with the same non-empty delimiter reproduces value exactly. The reverse does not hold in general: joining a list whose elements contain the delimiter and splitting again yields more pieces than you started with."

Everything else on the page checked out against the binary. The probe (`/tmp/plan-125-scratch/D-phase4/man-page-strings-split/probe.mfb`) confirmed: leading, trailing and adjacent empty pieces (`",a,,"` gives 4 elements `"", "a", "", ""`); no-match and longer-than-value delimiters give one element holding value unchanged; the empty string gives one empty element; matches are non-overlapping and resume after the whole delimiter (`"aaaa"` split on `"aa"` gives 3 empties, `"aaa"` gives `"", "a"`); matching is case-sensitive and byte-exact with no normalization (NFD `e\u{0301}x` is not split by NFC `"é"`); a multi-byte scalar delimiter splits cleanly; `separator :=` works as the named alias; an `AttributedString` from `astrings::fromString` returns the same 3 pieces as the `String`; and the empty delimiter raises code `77050002` with message "Argument value is not valid for the requested operation." before scanning, matching the lowering in `src/codegen/builtins/strings/func_split.rs`, which tests the delimiter length and branches to `raise_error("strings.split", "ErrInvalidArgument")` first. The two other examples printed `3` / `b` and `4` / `1` as the page implies. No banned vocabulary and no compiler-model sentences were found. The lowering also raises `ErrOutOfMemory` on allocation failure, which the derived Errors table omits, but that omission is shared by every allocating `strings` member and is a descriptor convention rather than a defect of this page's prose.
