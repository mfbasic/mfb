### 1. Grapheme-splitting matches are an omitted sharp edge
UNIT:      man-page:strings/contains
CLAIM:     "Because both are well-formed UTF-8 and UTF-8 is self-synchronizing, a matching byte run is always also a whole-scalar substring — a match can never land mid-scalar."
VERDICT:   incomplete
EVIDENCE:  The sentence reassures about scalar boundaries but is silent on grapheme boundaries, which is the boundary a developer actually sees on screen. Probe `/tmp/plan-125-scratch/D-phase4/man-page-strings-contains/graph.mfb` (built with `mfb init` + `mfb build`, run `p_graph/build/p_graph.out`) printed `TRUE` for all three of: `contains("e\u{0301}", "e")` (the bare base letter inside "é" written as e + combining acute), `contains("👨\u{200D}👩", "👨")` (one person inside a ZWJ family sequence), and `contains("🇺🇸", "🇺")` (one regional-indicator half of a flag). The companion probe `edges.mfb` printed `FALSE` for `contains("cafe\u{0301}", "\u{00E9}")` (decomposed vs precomposed é). Together these are the two-sided sharp edge the page's own checklist demands ("Unicode scalar or grapheme?"): a match CAN land in the middle of a user-perceived character, and two spellings of the same visible character do NOT match. "No normalization" is true but does not tell the reader either of these outcomes.
SUGGESTED: Replace the sentence with: "Matching is by Unicode scalar, not by user-perceived character: a match always covers whole scalars, but it can begin or end inside a combining sequence, an emoji sequence, or a flag — `contains("e" + combining acute, "e")` is `TRUE`. Because no normalization is applied, `"é"` written as one precomposed scalar does not match `"é"` written as `e` plus a combining acute."

### 2. Scan-order narration is implementation detail, not developer-visible behavior
UNIT:      man-page:strings/contains
CLAIM:     "The bytes of needle are compared against value at each successive byte offset, and the scan returns TRUE at the first offset where the whole needle matches."
VERDICT:   out-of-scope
EVIDENCE:  `src/codegen/builtins/strings/func_contains.rs:lower` does exactly this (a byte-offset loop ending at `emit_string_byte_range_equal_branch`), so the sentence is true. But the function returns a `Boolean`; the offset at which the scan stops, and the direction it scans, are unobservable to an MFBASIC program. Per `.ai/man-content.md` §1 ("if a sentence only matters to someone reading compiler source, it does not belong on the page") the developer-visible fact is only "comparison is exact, byte for byte", and the "self-synchronizing UTF-8" justification in the next sentence is likewise encoding theory rather than something a developer needs. The first sentence of the paragraph already states the contract.
SUGGESTED: Cut the sentence, and fold the byte-exactness into the next paragraph: "Comparison is exact: no normalization, case folding, or other transformation is applied to either operand, so `contains("Hello", "hello")` is `FALSE`." (That last outcome is verified by `edges.mfb`, which printed `FALSE` for the case probe.)
