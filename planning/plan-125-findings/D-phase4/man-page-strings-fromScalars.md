### 1. "generally larger" understates the ASCII case and overstates the rest
UNIT:      man-page:strings/fromScalars
CLAIM:     "Each element contributes one to four bytes depending on its code point, so the byte length of the result is generally larger than the element count, while len of the result equals the element count exactly."
VERDICT:   misleading
EVIDENCE:  Probe at /tmp/plan-125-scratch/D-phase4/man-page-strings-fromScalars/probe.bas, built with `mfb build -q p_probe` and run: `[`a`, `b`]` gives `ascii bytes=2` (equal to the element count, not larger); `[e, U+0301, a]` gives `count=3 len=3 bytes=4`. The precise relation is "never smaller than the element count, and equal when every scalar is ASCII". "Generally larger" is wrong for the most common input (plain ASCII) and gives no bound for the rest.
SUGGESTED: "Each element contributes one to four bytes depending on its code point, so `strings::byteLen` of the result is never smaller than the element count (it is equal only when every scalar is ASCII), while `len` of the result equals the element count exactly."

Everything else on the page checks out against the binary. Both examples compiled and ran from `mfb init` projects: the first printed `hi!`, the second printed `TRUE`. The probe confirmed the empty list yields a zero-length string, a U+0000 scalar is kept (three scalars in, `len` 3 and `byteLen` 3 out), `len` counts scalars rather than graphemes so the "equals the element count exactly" claim holds for a combining sequence, and the input list is unchanged after the call (`len(l)` still 3). The lowering in `helper_scalar_seam.rs` (`__strings_fromScalars`) appends each scalar's code point and calls `encoding::utf32Decode` with an unreachable TRAP, matching the page's claim that encoding always succeeds; the descriptor declares no errors and the rendered page has no Errors table, which is consistent.
