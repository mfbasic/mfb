### 1. `encoding::utf8EncodeBytes` does not exist
UNIT:      man-page:strings/toBytes
CLAIM:     "toBytes is the inverse of toString(List OF Byte) and the foundation the encoding package's Unicode codecs are built on; encoding::utf8EncodeBytes produces the same octets for the same string."
VERDICT:   wrong
EVIDENCE:  Probe under /tmp/plan-125-scratch/D-phase4/man-page-strings-toBytes/p_probe calling `encoding::utf8EncodeBytes(s)` fails to compile: `error[2-201-0011 SYMBOL_UNKNOWN_IDENTIFIER]: Built-in package `encoding` does not export `encoding.utf8EncodeBytes``. `grep -rn 'name: "utf8Encode' src/codegen/builtins/encoding/` finds only `utf8Encode` (`func_utf8_encode.rs:77`); `grep -rn utf8EncodeBytes src/` hits only this descriptor. With the real name, `encoding::utf8Encode("a€😀")` printed the same bytes as `strings::toBytes` (both round-trip to `a€😀`, both length 8). Because See-also is derived by scanning `desc` for `pkg::name` tokens (`src/cli/man.rs:render_see_also` / `referenced_functions`), the page also renders a dangling See-also entry `encoding::utf8EncodeBytes`, and `mfb man encoding utf8EncodeBytes` has no page. The "foundation the codecs are built on" clause is also a compiler-internals claim a developer cannot observe (§3).
SUGGESTED: "`toBytes` is the inverse of `toString(List OF Byte)`: `toString(strings::toBytes(s))` gives back `s`. `encoding::utf8Encode` returns the same bytes for the same string."

### 2. "Storage"/"backing" framing teaches a shared-buffer model
UNIT:      man-page:strings/toBytes
CLAIM:     "The string whose UTF-8 storage is returned." (parameter `value`) and "Return the raw UTF-8 bytes backing a string, one element per byte." (intro)
VERDICT:   misleading
EVIDENCE:  Descriptor `src/codegen/builtins/strings/func_to_bytes.rs:INTRO` and the `value` `Parameter.desc`. No banned word, but "storage is returned" and "bytes backing a string" describe the string's memory rather than its encoding, which is why the description then has to spend a paragraph undoing the implication ("its own value, so mutating it does not affect the string"). Probe confirms the copy: `MUT m = strings::toBytes(src)`, `m = collections::set(m, 0, toByte(72))` printed `Hi` for `m` and `hi` for `src`. The developer-visible fact is simply "the UTF-8 encoding of the string" (spec: strings are always UTF-8; `mfb man encoding utf8Encode` already says it that way).
SUGGESTED: intro: "Return a string's UTF-8 encoding as a list, one element per byte." Parameter: "The string to encode. Any `String` is accepted, including the empty string, which gives an empty list."

Everything else on the page checked out against the release binary. Both examples compiled and ran from their own `mfb init` projects: the first printed `6` then `195`, the second printed `hi`. The edge-case probe printed `0` for the empty string; `8`, `8`, `3` for `len(bytes)`, `strings::byteLen`, and `len(s)` on `"a€😀"` (1+3+4 bytes, matching the two/three/four-byte claim); `toString(bytes)` printed `a€😀` and `toString(back) = s` printed `TRUE` (inverse claim holds); the `AttributedString` overload on `astrings::fromString("hé")` printed `hé` through `toString` of its bytes; and a non-literal argument built via `strings::join` took the runtime path and printed `a€😀z`. The empty Errors table is consistent with the rest of `strings`: no page lists `ErrOutOfMemory` in a derived table (`mfb man strings --all | grep ErrOutOfMemory` hits only padLeft/padRight prose), so its absence here is the package convention, not a finding.
