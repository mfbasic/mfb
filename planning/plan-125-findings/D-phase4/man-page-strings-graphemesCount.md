### 1. Non-BMP characters do not make the cluster count differ from `len`
UNIT:      man-page:strings/graphemesCount
CLAIM:     "For text with combining marks, emoji, or characters outside the Basic Multilingual Plane, all three can differ: "e" plus U+0301 plus "fg" has three clusters but four scalars."
VERDICT:   misleading
EVIDENCE:  Probe at /tmp/plan-125-scratch/D-phase4/man-page-strings-graphemesCount/p/src/main.mfb, built with `mfb build .` and run: `astral gc=1 len=1 bytes=4` for `"\u{1F600}"`. A character outside the BMP is one scalar and one cluster; only `byteLen` diverges. Being outside the BMP has no effect on the cluster/scalar relationship, which is what this page is about. The cases that actually separate clusters from scalars in the probe were combining marks (`gc=3 len=4`), regional-indicator flags (`gc=1 len=2`), ZWJ emoji sequences (`gc=1 len=5`), skin-tone modifiers (`gc=1 len=2`), Hangul jamo (`gc=1 len=3`) and keycaps (`gc=1 len=3`). Listing "characters outside the BMP" alongside them tells a developer that 😀 alone will count differently from `len`, which it does not.
SUGGESTED: "The count is therefore a third measure, distinct from both `len(value)`, which counts Unicode scalar values, and `strings::byteLen(value)`, which counts UTF-8 bytes. A cluster and a scalar differ only when several scalars combine into one user-perceived character — combining marks, flags, emoji modifier and joiner sequences, Hangul jamo; a single emoji outside the Basic Multilingual Plane is still one scalar and one cluster, and only its byte length differs. `"e"` plus `U+0301` plus `"fg"` has three clusters but four scalars."

### 2. CR LF is one cluster; the page does not say so
UNIT:      man-page:strings/graphemesCount
CLAIM:     "An extended grapheme cluster is one user-perceived character, and it may be built from several Unicode scalar values: a base letter followed by combining marks, a flag formed from a pair of regional indicators, or an emoji built from a base symbol joined to modifiers by zero-width joiners. Each such cluster counts as one."
VERDICT:   incomplete
EVIDENCE:  Same probe: `crlf gc=3 len=4` for `"a\r\nb"`. The `\r\n` pair is a single extended grapheme cluster, so a developer using `graphemesCount` on Windows-style text gets one fewer than `len` per line ending. None of the three listed shapes hints that a control-character pair counts as one, and it is the one case that has nothing to do with "user-perceived characters" as the page defines them.
SUGGESTED: Append to that paragraph: "The pair `"\r\n"` is also a single cluster, so text with Windows line endings counts one cluster per line break, not two."

Everything else on the page verified against the binary. Both examples compiled with `mfb build .` and printed `3`/`3` and `3`/`4` as the page implies. Empty string returned `0`; `len(strings::graphemes(s))` matched `graphemesCount(s)` on all nine probe inputs (the lowering in `func_graphemes_count.rs` builds the graphemes list and reads its count, so the equality and the "cost grows with length" sentence both hold by construction); the Errors table is empty and the descriptor registers `errors: vec![]`; `astrings::fromString("e\u{301}fg")` passed directly to `graphemesCount` returned `3`. No banned vocabulary and no borrow/ownership mental model on the page.
