### 1. Grapheme sharp edge is missing: a match can land inside a combining sequence
UNIT:      man-page:strings/startsWith
CLAIM:     "Because both operands are well-formed UTF-8 and UTF-8 is self-synchronizing, a matching byte prefix is always also a whole-scalar prefix — a match can never land mid-scalar."
VERDICT:   incomplete
EVIDENCE:  The sentence is true (lowering: `gen_strings_support.rs:lower_string_prefix_predicate` does a length check then a byte-range compare), but §2 of `.ai/man-content.md` requires the scalar-vs-grapheme edge to be stated, and the page says only what a match can never split, not what it can. Probe `/tmp/plan-125-scratch/D-phase4/man-page-strings-startsWith/probe.bas` (built with `mfb init` + `mfb build`, run from `build/*.out`): `startsWith("é", "e")` with precomposed U+00E9 printed `FALSE`; `startsWith("e\u0301x", "e")` with decomposed e + U+0301 (bytes `65 cc 81 78`, confirmed by xxd) printed `TRUE`. So a prefix can match the base letter of a grapheme cluster and leave the combining mark behind, and two strings that display identically give different answers. "No normalization" hints at this but never states the observable consequence.
SUGGESTED: Append after the mid-scalar sentence: "It can, however, land inside a user-perceived character: `startsWith("e\u0301x", "e")` (a decomposed é) is `TRUE` because the prefix matches the base letter and stops before the combining mark, while the precomposed `startsWith("é", "e")` is `FALSE`. Normalize both operands first if you need the two spellings to agree."

### 2. "self-synchronizing" is encoding theory, not a developer term
UNIT:      man-page:strings/startsWith
CLAIM:     "Because both operands are well-formed UTF-8 and UTF-8 is self-synchronizing, a matching byte prefix is always also a whole-scalar prefix"
VERDICT:   misleading
EVIDENCE:  Same sentence as finding 1. The guarantee is correct, but the justification is a property of the encoding that a developer at the terminal need not know; the page is explaining *why* the compiler is allowed to compare bytes rather than *what* the developer observes (§1 test). Not a banned-word hit: `scripts/man-census.sh --banned-list` grep over the rendered page matched only the permitted word "value".
SUGGESTED: "A match always ends on a whole character's encoding — it can never stop partway through one — so comparing bytes gives the same answer as comparing characters."

All other sentences verified against the binary. Both page examples were compiled and run from `/tmp/plan-125-scratch/D-phase4/man-page-strings-startsWith/p_ex1` and `p_ex2`; they printed `TRUE`, `TRUE`, `FALSE` and `TRUE` respectively, matching the page. The boundary probe printed `TRUE` for `("", "")`, `FALSE` for `("", "a")`, `FALSE` for `("a", "abc")`, `TRUE` for `("abc", "abc")`, and both operands printed unchanged afterwards, confirming the empty/longer-prefix/unmodified claims. The `AttributedString` overload probe returned `TRUE` for `("Hello" attributed, "He")` and `FALSE` for `"he"`, matching the String results; a second probe passing an `AttributedString` as `prefix` was rejected at compile time with `TYPE_CALL_ARGUMENT_MISMATCH`, consistent with the page promising the overload only for `value`. The descriptor declares no errors and the lowering has no raise path, so "the call never fails" holds.
