### 1. `astrings::AttributedString` is not a spellable type name
UNIT:      man-page:strings/endsWithAny
CLAIM:     "value may also be an astrings::AttributedString: the query runs on its visible text and returns exactly what the String overload returns (same value, type, and errors)."
VERDICT:   misleading
EVIDENCE:  The prose renders the type in code font as `astrings::AttributedString`, but that spelling does not compile. Probe `/tmp/plan-125-scratch/D-phase4-current/man-page-strings-endsWithAny/p_probe/src/main.mfb` with `LET a AS astrings::AttributedString = astrings::fromString("hello.txt")` failed: `error[2-201-0011 SYMBOL_UNKNOWN_IDENTIFIER]: Built-in package `astrings` does not export `astrings.AttributedString``. Changing it to `LET a AS AttributedString` (the spelling the `astrings::fromString` example uses) compiled and printed `attributed: TRUE`, confirming the overload itself behaves as stated. The derived See also entry `astrings::AttributedString` is also not a renderable page: `mfb man astrings AttributedString` prints `error: unknown astrings function `AttributedString``, and `mfb man astrings types` lists no record by that name (`mfb man astrings types | grep AttributedString` is empty). The same spelling appears on the `strings::endsWith` page and the `astrings` overview, so this is a package-wide convention, but on this page a reader copying the identifier gets a compile error.
SUGGESTED: "`value` may also be an `AttributedString` (see `mfb man astrings`): the query runs on its visible text and returns exactly what the `String` overload returns." The See also row is derived; if it is meant to be a link, it should resolve to `mfb man astrings` or `mfb man astrings types`, which is a descriptor fix rather than a prose fix.

### 2. "same ... errors" promises parity on an error set that is empty
UNIT:      man-page:strings/endsWithAny
CLAIM:     "returns exactly what the String overload returns (same value, type, and errors)"
VERDICT:   misleading
EVIDENCE:  The descriptor in `src/codegen/builtins/strings/func_ends_with_any.rs` (`register`) declares `errors: vec![]`, the page renders no Errors table, and the Description says two paragraphs earlier that "the call is total — it never fails." Telling the reader the AttributedString overload raises "the same errors" invites them to look for an error set that does not exist. Probe output confirms the no-error path for every edge tested (empty list, empty candidate, longer candidate, combining mark, case mismatch, AttributedString): all printed a Boolean, `rc=0`.
SUGGESTED: "...returns exactly what the `String` overload returns: the same `Boolean`, and it still never fails."

No other findings. Every behavioral sentence checked true against the binary. The probe at `/tmp/plan-125-scratch/D-phase4-current/man-page-strings-endsWithAny/probe.mfb` printed: `emptyList/emptyValue: FALSE`, `emptyCandidate: TRUE`, `emptyCandidate/emptyValue: TRUE`, `longerSkipped: TRUE` (longer first entry skipped, later `"bc"` matched), `longerOnly: FALSE`, `combiningMark: TRUE`, `precomposedVsDecomposed: FALSE`, `caseFold: FALSE`, `wholeValue: TRUE`, `list: TRUE len=2` (list unchanged), `attributed: TRUE`. Both page examples compiled unchanged and printed `TRUE` and `FALSE` respectively, matching the captions. The lowering in `src/codegen/builtins/strings/gen_with_any.rs` (`lower_strings_with_any`, `suffix = true`) confirms list-order scan, first-match exit, `branch_hi` skip for a candidate longer than `value`, and a plain byte-range compare with no folding. No banned memory vocabulary and no compiler-internal sentences appear on the rendered page.
