### 1. `astrings::AttributedString` as written does not resolve as a type
UNIT:      man-page:strings/graphemes
CLAIM:     "value may also be an astrings::AttributedString: the query runs on its visible text and returns exactly what the String overload returns (same value, type, and errors)."
VERDICT:   misleading
EVIDENCE:  Behavior is true: probe `/tmp/plan-125-scratch/D-phase4-current/man-page-strings-graphemes/p_probe/src/main.mfb` with `LET a AS AttributedString = astrings::fromString("👍🏽é")` then `strings::graphemes(a)` printed `attr graphemes=2 first=👍🏽`. But the name the page uses does not compile: the same probe with `LET a AS astrings::AttributedString = ...` failed with `error[2-201-0011 SYMBOL_UNKNOWN_IDENTIFIER] ... Built-in package `astrings` does not export `astrings.AttributedString``. The declaration on `mfb man astrings fromString` is `AS AttributedString`, unqualified. The descriptor (`src/codegen/builtins/strings/func_graphemes.rs:DESC`) only lists a `String` implementation; the AttributedString acceptance comes from elsewhere, so a reader has only this sentence to go on, and it hands them a spelling that errors. (The derived See-also row uses the same `astrings::AttributedString` form, which is a man-page cross-reference convention, not a type name a program can write.)
SUGGESTED: "`value` may also be an `AttributedString` (see `mfb man astrings types`): the query runs on its visible text and returns exactly what the `String` overload returns (same value, type, and errors)."

### 2. Counting advice omits the function that exists for counting
UNIT:      man-page:strings/graphemes
CLAIM:     "This is a third way of counting a string, distinct from both of the others: len(value) counts Unicode scalar values and strings::byteLen(value) counts UTF-8 bytes."
VERDICT:   incomplete
EVIDENCE:  `strings::graphemesCount` exists (`src/codegen/builtins/strings/func_graphemes_count.rs`, `name: "graphemesCount"`) and returns the same count without building a list; probe printed `graphemes=N ... count=N` identical for all 11 inputs (e.g. `hangul graphemes=1 len=3 byteLen=9 count=1`). `strings::graphemeAt` also exists (`func_grapheme_at.rs`). The derived See-also lists only `astrings::AttributedString` and `strings::byteLen`, so nothing on the page tells the reader that `len(strings::graphemes(s))` has a direct equivalent. The page frames itself as "a way of counting" yet names the wrong tool for counting.
SUGGESTED: "This is a third way of measuring a string, distinct from both of the others: `len(value)` counts Unicode scalar values and `strings::byteLen(value)` counts UTF-8 bytes. To count clusters without building the list, use `strings::graphemesCount`; to fetch one cluster by position, use `strings::graphemeAt`."

### 3. Second example demonstrates nothing grapheme-specific
UNIT:      man-page:strings/graphemes
CLAIM:     "Iterate over user-perceived characters:" (example using `strings::graphemes("héllo")`)
VERDICT:   misleading
EVIDENCE:  Compiled and ran: output `h é l l o`, exit 0, so the example works. But `printf 'héllo' | od -An -tx1` gives `68 c3 a9 6c 6c 6f`: the é is the precomposed U+00E9, one scalar. Probe row `precomposed graphemes=1 len=1 byteLen=2` confirms every element here is a single scalar, so `strings::toScalars` iteration would print identically. The example is framed as the reason to prefer `graphemes` over scalar iteration, yet shows no case where they differ. Probe row `decomposed graphemes=1 len=2 byteLen=3` (e + U+0301) is the case the sentence is actually about.
SUGGESTED: Keep the program but make the string carry a combining mark and say so, e.g. introduce it as "Iterate over user-perceived characters — the `é` here is `e` followed by a combining acute accent, two scalars but one cluster:" and build the string with `"he" & strings::fromScalars([toScalar(769)]) & "llo"` (or an equivalent literal), so the loop visibly prints five lines, not six.

No other findings. Verified true by probe (`p_probe`, built with `mfb build -q .`, run `./build/p_probe.out`): the family ZWJ sequence plus `x` yields 2 clusters from 8 scalars on both the compile-time constant path and a runtime-built string (`family-const` and `family-rt` rows both `graphemes=2 len=8 byteLen=26`); empty string yields the empty list (`emptylen=0`); two flags yield 2 clusters from 4 scalars; skin-tone modifier, keycap sequence, Hangul jamo and CR LF all cluster per UAX #29 (CRLF row `graphemes=3 len=4`); `strings::join(parts, "")` equals the input for every row (`roundtrip=TRUE`); `collections::set` on the returned list left the source string unchanged (`after-mutating-list src=ab`). Example 1 printed `3`, the family emoji, and the flag, as the page implies. No banned memory vocabulary and no compiler-internal sentences on the page.
