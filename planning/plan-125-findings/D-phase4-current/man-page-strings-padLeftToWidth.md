### 1. A tab in `value` is counted as one column, so a tabbed value will not line up
UNIT:      man-page:strings/padLeftToWidth
CLAIM:     "It uses the same column rules as term::measureText without requiring an active terminal surface, so this is the member that lines a table up on screen."
VERDICT:   incomplete
EVIDENCE:  Probe `/tmp/plan-125-scratch/D-phase4-current/man-page-strings-padLeftToWidth/p_edge/src/main.mfb`, line `try("tab value", "a<TAB>b", 6, "-")` printed `tab value -> [---a	b] len=6`: three dashes were added, so the tab was measured as exactly one column. A terminal advances a tab to the next tab stop, so a row whose value contains a tab (or any control character) will not line up with its neighbours even though the result "fills" `columns`. The measure is `measure_text_of` in `src/codegen/builtins/term/func_measure_text.rs` (shared by `term::measureText` and the pad helper's `term::measureTextRaw`), which sums per-cluster `charwidth` values and never expands tabs. The page's sharp-edge list covers raise-vs-clamp, scalars-vs-columns, truncation and mutation, but not this. Minor: arguably `term::measureText`'s page should own the rule, but this page makes the "lines a table up" promise, and a one-clause caveat keeps it honest.
SUGGESTED: Append to that paragraph: "The measure counts printable text only — a tab or other control character in `value` is not expanded to a tab stop, so a value that contains one will not line up with its neighbours."
