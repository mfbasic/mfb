### 1. A tab or newline inside `value` counts as one column, so the padded row does not line up
UNIT:      man-page:strings/padRightToWidth
CLAIM:     "It uses the same column rules as `term::measureText` without requiring an active terminal surface, so this is the member that lines a table up on screen."
VERDICT:   incomplete
EVIDENCE:  Probe `/tmp/plan-125-scratch/D-phase4-current/man-page-strings-padRightToWidth/edges.mfb` (built via `mfb init` + `mfb build -q`, run `p_edges/build/p_edges.out`): `strings::padRightToWidth("a\tb", 6, "-")` printed `[a<TAB>b---]` (6 scalars) and `strings::padRightToWidth("a\nb", 6, "-")` printed `[a` / `b---]`. The tab and the newline were each counted as a single column, so the "6-column" result occupies far more than six cells on a real terminal. Source: `helper_pad_to_width.rs:__strings_padToWidthCopies` measures with `term::measureTextRaw`, which lowers through the same `measure_text_of` as `term::measureText` (`src/codegen/builtins/term/func_measure_text.rs:lower_measure_text_raw`); neither this page nor `mfb man term measureText` says what a control character measures. Every other claim on the page was verified true (see the no-findings paragraph below).
SUGGESTED: Append to the first paragraph of the description: "Only printable text lines up: a tab, newline or other control character inside `value` counts as one column, so a value that contains one will not line up however it is padded."

Everything else on the page verified true against the binary. Both examples compiled and ran under `mfb build -q` (`p_ex1`, `p_ex2`) and printed `|ascii     |end|`, `|日本語    |end|`, `|café      |end|` and `[x😀😀]`, `日本語`, exactly as the page implies. The error probe `errs.mfb` raised `77050002 Argument value is not valid for the requested operation.` for a negative `columns`, an empty `padChar` (even when no padding was needed), a two-scalar `padChar` (`ab`, `e\u{301}`, `👍🏽`), and a zero-width `padChar` (combining mark, ZWJ, tab, BEL), while a ZWJ inside `value` padded normally. `huge.mfb` and `huge2.mfb` with `columns` at the Integer maximum and at 2^62 with an emoji `padChar` each raised `77010001 Allocation failed.`. `edges.mfb` confirmed `0` never pads, an already-wide value comes back unchanged, undershoot (`"x",6,"😀"` gives three scalars, `"x",7,"😀"` gives four), `"ab",9,"日"` gives `ab日日日`, and the original binding is unchanged after the call. `attr.mfb` and `attr2.mfb` confirmed the AttributedString overload: `**日本**` padded to 8 rendered via `astrings::toMarkdown` as `**日本**----`, so the styling of the kept text survives and the padding carries none. Both See-also targets (`mfb man strings padRight`, `mfb man term measureText`) render. The memory-vocabulary sweep found only the derived `Allocation failed.` Errors row, which is carve-out 2. I could not call `term::measureText` directly in the sandbox (it raises `7-705-0007` with no TUI), so the "same column rules" equivalence rests on the shared `measure_text_of` lowering plus the observed 2-column CJK/emoji and 1-column combining-sequence results, which match the rules the measureText page states.
