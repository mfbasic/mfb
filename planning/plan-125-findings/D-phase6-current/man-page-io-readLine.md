### 1. Backspace after a non-ASCII character on a terminal raises ErrEncoding, not "erases the last character"
UNIT:      man-page:io/readLine
CLAIM:     "The line ends at Enter; Backspace erases the last character; keys that type nothing — the arrows, Home, End, the function keys — and Escape are ignored rather than becoming part of the line."
VERDICT:   wrong
EVIDENCE:  Probe `p_loop` (loop of `io::readLine()` under TRAP, printing `got [..]` or `err code`) run on a pty via `script -q /dev/null`. Input `ab<DEL>c\n` → `got [ac]` (ASCII erase works). Input `\xc3\xa9<DEL>Z\n` (é, Backspace, Z) → `err 77020004 Text encoding or decoding failed.`; input `e\xcc\x81<DEL>Z\n` → same ErrEncoding. `script -q /dev/null stty -a` shows the pty default is `-iutf8`, and `grep -rin iutf8 src/codegen/io/` finds nothing: `gen_read_line_family.rs` ("`io::readLine` reads with echo off, the line discipline otherwise intact") leaves the kernel's byte-wise erase in charge, so Backspace removes one byte of a multi-byte character and the half-sequence then fails UTF-8 validation. In the keystroke path (`--app` window) the code comment at the `erase` label says "drop the line's last scalar", so a combining sequence needs one Backspace per scalar there too (UNVERIFIED by run: no `--app` window in this sandbox). This is also a binary bug (IUTF8 should be set while echo is off); the main thread should file it.
SUGGESTED: Until the binary is fixed, the page must say what happens: "Backspace erases the previous Unicode scalar, so a character typed as a base letter plus a combining mark takes two presses. On a terminal whose line discipline erases bytes rather than characters (the macOS default), Backspace after a non-ASCII character leaves an ill-formed sequence and the read raises ErrEncoding." After the fix, "Backspace erases the previous Unicode scalar" alone.

### 2. ErrEncoding discards the rest of the line; the page does not say so
UNIT:      man-page:io/readLine
CLAIM:     "Either way the text must be valid UTF-8: an ill-formed sequence raises ErrEncoding rather than being dropped or replaced, because a line with a byte silently missing would look complete."
VERDICT:   incomplete
EVIDENCE:  `printf 'ab\xffcd\nok\n' | ./p_loop.out` → `err 77020004`, then `got [ok] len=2`: the bytes `cd` after the bad byte are never returned, and the next call starts at the next line. Matches the `BAD_LINE` comment in `gen_read_line_family.rs` ("consumes the WHOLE line through its LF and raises `ErrEncoding` once when it ends ... so the next call starts at the next line"). The page says nothing about where the next read resumes, which is the sharp edge a developer handling the error needs.
SUGGESTED: Append: "The whole offending line is read through its line feed before the error is raised, so none of it is returned and the next call starts at the following line."

### 3. Three rows of the Errors table have no raising condition anywhere on the page
UNIT:      man-page:io/readLine
CLAIM:     Errors table rows `77010001 ErrOutOfMemory`, `77020005 ErrInputFailed`, `77050020 ErrWrongMode`.
VERDICT:   incomplete
EVIDENCE:  The Description names ErrEncoding, ErrTimeout, ErrInvalidArgument, ErrWriteFailed, ErrEndOfFile and ErrInvalidContext (`mfb man io readLine | grep -c Err`) but never ErrInputFailed, ErrOutOfMemory or ErrWrongMode. `func_read_line.rs:131` lists `"ErrWrongMode"` in the descriptor's `errors`, and `gen_read_line_family.rs:815-825` wires `input_error` → ErrInputFailed and `alloc_error` → ErrOutOfMemory. The only hint of ErrWrongMode's condition is buried in the derived message column (`--app` build in `app::Mode.None`). The standard requires "every raisable error and the condition that raises it" in the prose. Probing: closed stdin (`./p_loop.out <&-`) and `/dev/null` both raise ErrEndOfFile, so I could not trigger ErrInputFailed; its condition (a failed read of standard input that is not end of input) comes from the lowering, UNVERIFIED by run.
SUGGESTED: Add to the Description: "In an `--app` build the program must be in `app::Mode.Console` or `app::Mode.Canvas`, otherwise the call raises ErrWrongMode. A read of standard input that fails for a reason other than end of input raises ErrInputFailed; running out of memory while the line grows raises ErrOutOfMemory."

### 4. Parameter description does not say what a negative value does
UNIT:      man-page:io/readLine
CLAIM:     "Must not be negative." (timeoutMs parameter description)
VERDICT:   incomplete
EVIDENCE:  `printf 'x\n' | ./p_tneg.out` with `io::readLine(-1)` → `err 77050002 Argument value is not valid for the requested operation.` The Description paragraph does say "A negative timeoutMs raises ErrInvalidArgument", but the parameter cell, which the standard says must itself cover zero/empty/negative, only forbids it without naming the outcome. The cell is also shared verbatim with `readRaw` (`TIMEOUT_DESC` from `func_read_raw.rs`), so the fix lands on every reader.
SUGGESTED: "A negative value raises ErrInvalidArgument."

Everything else on the page checked true against the binary. Verified by probe: empty line returns `""`; CRLF → CR removed, bare CR mid-line kept, `\r\r\n` keeps one CR; escape and NUL bytes in piped data are plain bytes; mid-line EOF returns the partial line and the next call raises ErrEndOfFile; EOF before any byte raises ErrEndOfFile; `readLine(0)` with no data ready raises ErrTimeout and with data ready returns it; a 300 ms timeout on `par` + 1 s + `tial\n` raises ErrTimeout and the following `readLine()` returns `partial`; a worker thread without `thread::openStdIn` gets code 77050019 ErrInvalidContext; arrows typed on a pty are ignored; all three examples compile and produce the output the page implies (`Passphrase: ` followed by a newline with the typed text absent; the 5 s example prints `no answer; continuing` on timeout and `you said yes` otherwise). The `--app` window claims and the echo-suppression claim could not be fully checked here: on the pty the first line was echoed because it arrived before the read began, and later lines were not, which is consistent with the page but not a clean test.
