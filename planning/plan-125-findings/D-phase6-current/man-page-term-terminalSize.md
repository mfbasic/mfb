### 1. The resize sibling is never named
UNIT:      man-page:term/terminalSize
CLAIM:     "A program that lays out, centres, or bounds-checks against these dimensions should ask again rather than cache the first answer."
VERDICT:   incomplete
EVIDENCE:  The page tells the reader to poll but never names `term::didResize`, the read built for exactly this ("Report whether the terminal was resized since the last check", `src/codegen/builtins/term/func_did_resize.rs:INTRO`). Both neighbours already point the other way: `mfb man term sync` says "term::didResize reports the change afterwards, and term::terminalSize gives the new extent", and `mfb man term didResize` says "A companion term::terminalSize call returns the new extent after term::didResize reports a change". The derived See also list on this page (`mfb man term terminalSize`) has app::Mode, TermSize, isOn, off, on, sync and no didResize, because the description never mentions it. §2 requires the cross-reference to the sibling a developer would otherwise reach for.
SUGGESTED: Append to that paragraph: "`term::didResize` reports whether the size changed since its last call, so a program can poll it each frame and call `term::terminalSize` again only when it answers TRUE."

### 2. The zero-size rule is stated for the console only, and app mode does not apply it
UNIT:      man-page:term/terminalSize
CLAIM:     "If the terminal cannot say — standard output is not a terminal, or the host does not answer — or if it reports zero rows or zero columns, the call raises ErrUnsupported."
VERDICT:   incomplete
EVIDENCE:  The console emitter checks both counts (`src/codegen/term/core/term/mod.rs:emit_terminal_size`, `compare_immediate(&rows,"0") / branch_eq(&unsupported)` and the same for `cols`), and the probe confirms it: under `script -q /dev/null ./proj_ex1/build/ex1.out` the pty reports `stty size` = `0 0` and the program traps with `Error: 7-705-0007 ... Location: src/main.mfb:6:32`. The three app-mode emitters have no such check: macOS reads `TV_COLS_OFFSET`/`TV_ROWS_OFFSET` straight into the record (`src/target/macos_aarch64/app/app_io.rs:emit_app_terminal_size`), Linux reads `ST_TERM_COLS`/`ST_TERM_ROWS` (`src/target/linux_gtk/app_io.rs:emit_app_term_terminal_size`), Windows calls `emit_win_grid_size` (`src/target/win_x86_64/app/mod.rs:emit_term_size`). The app paragraph lists only "TUI mode is off or no view is attached" as its ErrUnsupported conditions, so whether a zero count can ever surface in app mode is left to the reader. UNVERIFIED at runtime: no `--app` build can be driven in this sandbox, so I did not observe a zero count being returned, only that nothing in the emitted code refuses one.
SUGGESTED: Make the scope explicit in the console paragraph ("In a console program, if the terminal cannot say ... the call raises ErrUnsupported") and in the app paragraph state what app mode does with the view's counts: either "the counts are returned as the view reports them, with no zero check" or, if the view guarantees at least one cell, say that, so the reader knows the console-only rule does not carry over.

Everything else on the page checks out against the binary. Probes under `/tmp/plan-125-scratch/D-phase6-current/man-page-term-terminalSize` (built with `mfb build .` per project): example 1 in a 100-column, 40-row pty (`script -q /dev/null sh -c "stty rows 40 cols 100; ./proj_ex1/build/ex1.out"`) printed `100x40`; example 2 wrote `middle`; calling before `term::on` (`off.mfb`, with `isOn=FALSE` printed first), after `term::off` (`after_off.mfb`), and with stdout piped instead of a tty (`./proj_ex1/build/ex1.out | cat`) each trapped with `Error: 7-705-0007` (ErrUnsupported); two consecutive calls (`guarded.mfb`) returned `100x40 100x40`. The ErrWrongMode gate is in `src/codegen/builtins/term/gen_shared.rs:lower_term_helper` (presentation-mode check, no-op outside `--app`), the console ErrOutOfMemory path is the `alloc_error` label in `emit_terminal_size`, the macOS app alloc failure branches to `unsupported` as the page says, and `./scripts/man-census.sh --banned-list` terms do not appear on the rendered page outside the derived "Allocation failed." error message.
