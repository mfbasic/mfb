### 1. "Only what changed is sent" is not literally true — every present sends a fixed tail
UNIT:      man-page:term/sync
CLAIM:     "Only what changed is sent to the terminal. `term::sync` compares the frame you have composed against the one already on screen and updates just the cells that differ"
VERDICT:   misleading
EVIDENCE:  Probe `twice/src/main.mfb` (on, clear, moveTo, print "hello", sync ×3, off) vs `once/src/main.mfb` (same, sync ×1), both built with `mfb build -q`, run with stdout piped to `wc -c`: once = 2252 bytes, twice = 2284 bytes, so each extra sync with nothing changed emits 16 bytes. `od -c` on `twice` shows them: `\e[0m\e[2;1H\e[?25h` (SGR reset, cursor reposition, cursor visibility) repeated once per sync. Source: `src/codegen/term/grid/term_grid/present.rs:emit_grid_present`, the "Reset SGR, restore cursor position + visibility" block runs unconditionally after the diff loop. Also, the same emitter always re-emits a cell holding a pooled multi-code-point cluster even when unchanged (comment "always re-emit a pooled cell" in the diff loop). No cell glyphs are re-sent for plain text, so the diff itself is real; the sentence just overstates it.
SUGGESTED: "Only the cells that changed are sent to the terminal, plus a short fixed tail each frame that resets the colours and places and shows or hides the cursor. `term::sync` compares the frame you have composed against the one already on screen and re-sends just the cells that differ (a cell holding a multi-code-point grapheme cluster is always re-sent), so redrawing the whole surface every frame costs work proportional to what actually moved."

### 2. Resize path: `term::didResize` can report a resize that the surface did not take
UNIT:      man-page:term/sync
CLAIM:     "If the size cannot be re-read or the surface cannot be resized, the old surface is kept and the frame is presented into it unchanged."
VERDICT:   incomplete
EVIDENCE:  `src/codegen/term/grid/term_grid/resize.rs:emit_grid_resize`: the resize-flag latch ("latch the resize flag so `term::didResize()` reports it") is set as soon as the new size differs, *before* the new block is requested; the "Allocation failed → keep the old grid (skip the resize this frame)" branch comes after it and does not clear the latch. So in the "surface cannot be resized" case the page describes, `term::didResize` still returns TRUE on the next call while `term::terminalSize` (which reads the grid header) still gives the old extent. Not reproducible without exhausting memory, so UNVERIFIED by probe; the ordering is read from the emitter.
SUGGESTED: Append: "In that second case `term::didResize` still reports the change, so a program that resizes its layout on `term::didResize` should take its dimensions from `term::terminalSize`, which gives the size the surface actually has."

### 3. Cursor-position sentence: the example's own output shows the subtlety the page should name
UNIT:      man-page:term/sync
CLAIM:     "Each frame ends with the terminal's cursor at the surface's current position — where `term::moveTo` put it, or wherever the last `io::print`/`io::write` left it"
VERDICT:   incomplete
EVIDENCE:  Example 1 (`ex1/src/main.mfb`, the page's first example verbatim) built and run piped through `od -c`: the present ends with `\e[0m\e[2;1H\e[?25h`, i.e. the cursor is parked at row 2, column 1 (0-based (1,0)) — the start of the line *below* "hello", because `io::print` appends a line break. A reader following the first example and expecting the cursor to sit after "hello" will be surprised; the page says "wherever the last `io::print` left it" without saying that `io::print` leaves it on the next line while `io::write` leaves it after the text.
SUGGESTED: "...where `term::moveTo` put it, or wherever the last `io::print` (start of the following line) or `io::write` (just after the text) left it..."
