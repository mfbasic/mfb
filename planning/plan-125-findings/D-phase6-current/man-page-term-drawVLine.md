### 1. A run cell landing on half of a wide glyph also blanks the glyph's other half
UNIT:      man-page:term/drawVLine
CLAIM:     "it overwrites only the cells in the run, so a later draw over the same cell (for example a crossing horizontal line) wins."
VERDICT:   incomplete
EVIDENCE:  Probe `/tmp/plan-125-scratch/D-phase6-current/man-page-term-drawVLine/probe/src/main.mfb` draws `term::drawText(1, 0, "世界ab")` (the two-column glyph 世 occupies columns 0 and 1) and then `term::drawVLine(term::LineStyle.Heavy, 3, 1, -5)` on column 1. Rendered row 1 under a 24x80 pty (`python3 -I ptyrun.py probe/build/probe.out`) is ` ┃界ab` — column 0, which is not in the run, was cleared to a blank. The implementation does this on purpose: `emit_stamp_run` calls `emit_clear_wide_pair` for every run cell (`src/codegen/term/core/term/draw.rs:emit_stamp_run`, comment "clear the paired half of any wide glyph this run cell overwrites"). Every other claim in the sentence held: the crossing `term::drawHLine` drawn afterwards replaced the `║` at (1, 9) with `─`.
SUGGESTED: "it overwrites only the cells in the run, so a later draw over the same cell (for example a crossing horizontal line) wins. One exception: if a run cell lands on either half of a two-column glyph (such as 世), the glyph's other half is blanked too, so a line never leaves a half-character behind."

Everything else on the page checked out against the release binary. The probes and what they showed:

- **Both examples compile and run** (`mfb build -q .` in `ex1/` and `ex2/`, run under a 24x80 pty). Example 1 renders `║` in column 0 on all 24 rows; example 2 renders `│` in column 40 on rows 0 to 23. Note that example 1 raises error 7-705-0007 from `term::terminalSize` when the pty reports a 0x0 window (first attempt, `script` with no controlling tty). That is a property of `terminalSize`, not of this page, so it is not filed here.
- **Endpoint order, inclusivity and clamping** (`probe/`): rows 3 to -5 on column 1 drew rows 0 to 3; rows 6 to 2 on column 3 drew rows 2 to 6; rows 2 to 2 on column 7 drew the single cell. Column -1, column 80 (= columns), span 1000 to 2000 and span -10 to -1 each drew nothing and raised nothing. Matches `emit_stamp_run` and the page's wording exactly.
- **Glyph table**: `TERM_VLINE_CODEPOINTS` in `src/codegen/error/constants/error_constants.rs` is U+2502, 2503, 2506, 2507, 250A, 250B, 2551 in `LineStyle` ordinal order, which is the seven glyphs the page lists in that order.
- **Colours and attributes in effect**: the red `setForeground` was emitted as `38;2;255;0;0m` before the `║` and `─` glyphs in the raw stream.
- **No cursor move, no colour change, TUI-off gate** (`p2/` and `gate/`): after `drawVLine` on column 20, `io::write("X")` landed at (0, 0) and `getForeground` compared equal before and after; a program calling `drawVLine` without `term::on()` printed "gate ok, still running" with no error.
