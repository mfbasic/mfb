### 1. `term::on` discards a pending resize; the page never says so
UNIT:      man-page:term/didResize
CLAIM:     "The flag is cached: once a resize is detected it stays TRUE across every intervening call until term::didResize observes it, so a program that only polls occasionally never misses a resize."
VERDICT:   incomplete
EVIDENCE:  `src/codegen/term/core/term/screen_mode.rs` (the `term::on` reset list) writes `TERM_STATE_DID_RESIZE_OFFSET` to `0` alongside fg/bg/bold/underline/cursor. Probe `/tmp/plan-125-scratch/D-phase6-current/man-page-term-didResize/p_probe/src/main.mfb` (second version): `term::on; sync; sleep 600; sync; term::on; print didResize` run under a pty resized 24x80→30x100 at 0.3 s (`python3 -I pty.py ./p_probe/build/p_probe.out 0.3:30x100 0.9:40x120`) printed `reOnAfterLatchedSync=FALSE`. Same program with no resize also prints FALSE, so the latch was set by the second sync and then wiped by `term::on`. "Every intervening call" is therefore false for one call: `term::on`. The page's only statement about `on` is "Before any term::on … it simply reads FALSE", which does not cover a second `on`.
SUGGESTED: Append to that paragraph: "One call does clear it without reporting: `term::on` resets every `term::` state value to its default, the resize flag included, so a resize detected before a second `term::on` is not reported afterwards. `term::off` does not clear it — its final `term::sync` can still detect a resize, and the next `term::didResize` reports it." (The second half is from the same probe: `afterOffFinalSync=TRUE; again=FALSE` with a resize at 0.9 s before `term::off`, FALSE without one.)

### 2. "since the last time didResize was called" overstates when a resize is reported
UNIT:      man-page:term/didResize
CLAIM:     "term::didResize returns TRUE when the terminal (CLI) or window (--app) has changed size since the last time term::didResize was called, and FALSE otherwise."
VERDICT:   misleading
EVIDENCE:  In a console build the flag is only latched inside `term_grid::emit_grid_resize`, which `present.rs` calls at `term::sync` entry and nowhere else; `term::didResize` itself (`core/term/mod.rs:emit_did_resize`) only loads and zeroes the slot. Probe (first `p_probe` version, resize at 0.3 s, `sleep 600` then `didResize` with no `sync` in between) printed `noSyncYet=FALSE`, then `afterSync=TRUE` once a `term::sync` ran. So a terminal that has changed size "since the last call" still reads FALSE until the program presents a frame. The second paragraph does say sync re-reads the size, but the opening sentence states the unconditional rule and a reader stops there.
SUGGESTED: "term::didResize returns TRUE when a size change of the terminal (CLI) or window (--app) has been noticed since the last time term::didResize was called, and FALSE otherwise. In a terminal, a change is noticed only by term::sync (see below), so a resize that happens between two didResize calls with no term::sync between them is reported after the next term::sync, not before."

Everything else checked out. Verified by source read: not gated on `active` (`emit_did_resize` has no active test; `beforeOn=FALSE` by probe), app arm is `term.didResize` in `macos_aarch64/app/app_io.rs:emit_app_did_resize` with the `ErrWrongMode` gate prepended by `gen_shared::lower_term_helper` (the window-resize latch is `term_view.rs` storing `TV_DID_RESIZE_OFFSET`; no app window could be opened in the sandbox, so the live-window claim is source-read only). Both examples compile (`mfb build -q p_ex1`, `p_ex2`) and behave as the page implies under a pty: example 1 shows `reflowed` after a 0.5 s resize, example 2 prints `last seen 100x30` after a resize and `last seen 80x24` without one. No banned vocabulary and no compiler-model sentences on the page. One out-of-unit observation: example 2 aborts with ErrUnsupported (7-705-0007 at `term::terminalSize`) when stdout is not a tty, which is `terminalSize`'s documented contract and not a defect of this page.
