### 1. A run that lands on half of a wide glyph also blanks the other half
UNIT:      man-page:term/drawHLine
CLAIM:     "it overwrites only the cells in the run, so a later draw over the same cell (for example a crossing vertical line) wins."
VERDICT:   incomplete
EVIDENCE:  Console lowering `emit_stamp_run` calls `emit_clear_wide_pair` for every stamped cell (`src/codegen/term/core/term/draw.rs:emit_stamp_run`, `emit_clear_wide_pair`): if the cell is the trailing half of a wide glyph, the primary to its left is blanked to a space; if it is a wide primary, the trail to its right is blanked. Probe `/tmp/plan-125-scratch/D-phase6-current/man-page-term-drawHLine/probe/src/main.mfb` does `term::drawText(0, 0, "漢字abc")` then `term::drawHLine(term::LineStyle.Double, 0, 1, 1)` (a one-cell run on column 1 only). Run under `script -q probe.pty ./withsize.sh probe/build/probe.out` and decoded, row 1 reads `' ═字abc'`: column 0 (outside the run) became a space. The page says only the run's cells change, which is false whenever an endpoint splits a wide glyph (CJK, emoji). The app-mode helper `emit_term_draw_line_helper` (`src/target/macos_aarch64/app/term_view.rs`) contains no wide-pair clearing at all (`sed -n 1800,1950p … | grep -ci 'wide\|WIDE_TRAIL'` → 0), so the two backends appear to differ here; UNVERIFIED in app mode (no window in the sandbox), flagging for the main thread as a possible orphaned-half-glyph bug.
SUGGESTED: "it overwrites only the cells in the run, so a later draw over the same cell (for example a crossing vertical line) wins. One exception: if an end of the run lands on half of a double-width glyph (CJK, emoji), the glyph's other half is blanked to a space as well, so no orphaned half is left on the surface."

### 2. Example 2 does not produce the frame it promises
UNIT:      man-page:term/drawHLine
CLAIM:     "Frame a box with two horizontal and two vertical lines:"
VERDICT:   misleading
EVIDENCE:  Compiled and ran `/tmp/plan-125-scratch/D-phase6-current/man-page-term-drawHLine/ex2` (`mfb build -q ex2`; `ex2/build/ex2.out > ex2.raw`), decoded rows 1 and 11 read `'│───────────────────│'` and rows 2–10 `'│                   │'`. The four corner cells are `│`, not corner glyphs, because the vertical lines are drawn last and "a later draw wins" (the page's own rule). A reader who copies this expecting a framed box gets open corners; `term::drawBox` is the member that draws corners (`TERM_CORNER_*_CODEPOINTS`, `emit_draw_box`), and the page never points at it.
SUGGESTED: "Outline a box with two horizontal and two vertical lines (the corners are left as `│`, because the vertical lines are drawn last and win; use `term::drawBox` for a frame with real corner glyphs):" and add `term::drawBox` to the description so it lands in See also.
