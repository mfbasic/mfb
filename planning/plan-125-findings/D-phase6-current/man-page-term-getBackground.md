### 1. First sentence describes the foreground, not the background
UNIT:      man-page:term/getBackground
CLAIM:     "term::getBackground returns the colour that subsequently drawn text will be written in, as a color::Color."
VERDICT:   misleading
EVIDENCE:  The sentence is a verbatim copy of `func_get_foreground.rs:DESC` line 1 (`grep -n 'const DESC' -A 2 src/codegen/builtins/term/func_get_foreground.rs` prints the identical text). Text is "written in" its foreground colour; the background is the colour of the cell behind it, which is what `emit_set_color`/`emit_get_color` store at `TERM_STATE_BG_OFFSET` and what `func_set_background.rs:DESC` describes ("sets the background colour of the cells that subsequent ... text"). A reader who opens getForeground and getBackground side by side sees the same opening sentence on both and cannot tell which channel either reads.
SUGGESTED: "`term::getBackground` returns the colour that will fill the cells behind subsequently drawn text — their background, not the glyph colour — as a `color::Color`. It takes no arguments."

### 2. A setBackground made while TUI mode is off does not change what this call reports
UNIT:      man-page:term/getBackground
CLAIM:     "after a term::setBackground call its red, green and blue match the colour that was set (its alpha does not: that is always 255), until the next term::setBackground or the next term::on."
VERDICT:   incomplete
EVIDENCE:  `emit_set_color` (`src/codegen/term/core/term/attributes.rs`) starts with `emit_gate_inactive`, so a `setBackground` while off is dropped entirely. Probe `/tmp/plan-125-scratch/D-phase6-current/man-page-term-getBackground/probe/src/main.mfb`: `term::setBackground(color::rgb(9, 9, 9))` before `term::on()`, then `term::on()`, then `getBackground` prints `after-on 0,0,0,255`, not 9,9,9. The page's sentence has no "while on" qualifier, and the next paragraph only says that *getBackground* behaves specially while off, so a reader can conclude that setting the colour before `term::on` survives the switch-on. It does not.
SUGGESTED: "after a `term::setBackground` call made while TUI mode is on, its red, green and blue match the colour that was set (its `alpha` does not: that is always `255`), until the next `term::setBackground` or the next `term::on`. A `term::setBackground` made while TUI mode is off is ignored, so `term::on` always starts from black."

Everything else on the page verified against the binary. The probe above printed `off-initial 0,0,0,255`, `after-on 0,0,0,255`, `after-set-rgba(10,20,30,40) 10,20,30,255` (alpha from the set colour discarded, reported 255), `after-set-rgb(1,2,3) 1,2,3,255`, `after-off 0,0,0,255`, `after-on-again 0,0,0,255`. Both page examples compiled with `mfb build` and ran to exit code 0 (the second printed `warning`). Import claims were probed with three programs under the same scratch directory: `IMPORT term` alone with `LET c AS color::Color` fails with SYMBOL_UNKNOWN_IMPORT; `LET c = term::getBackground()` then `c.red` without `IMPORT color` fails with TYPE_CALL_ARGUMENT_MISMATCH/TYPE_UNKNOWN_VALUE; `LET c = term::getBackground()` passed straight back to `setBackground` compiles and runs without `IMPORT color`, matching the "no channel unpacking" wording. ErrOutOfMemory is raised only on the arena allocation of the returned record (`emit_get_color`, `raise_error_into(... "ErrOutOfMemory")`); the ErrWrongMode row is source-verified via `gen_shared.rs` (`prepend_wrong_mode_gate`, active only when `presentation_mode_offset` is `Some`) but UNVERIFIED by run, since I did not build an `--app` program. The banned-word grep over the rendered page hits only the derived Errors-table message "Allocation failed.", which is the §4.4 carve-out. No sentence teaches a borrow or ownership model.
