### 1. Three sibling pages contradict the overview and term::sync on when a frame is presented
UNIT:      man-pkg:term
PAGE:      package-wide (overview, sync, clear, hideCursor, showCursor)
CATEGORY:  consistency
CLAIM:     Overview: "nothing appears until the program calls term::sync, the one operation that presents a frame." Sync page: "term::sync is the one and only operation that presents a frame while the program runs" and lists "term::showCursor/term::hideCursor" among calls that touch "the terminal not at all". Clear page: "a Linux --app build repaints from the clear itself." hideCursor: "a Linux --app build repaints from this call itself." showCursor: "a Linux --app build repaints from this call itself."
VERDICT:   inconsistent
EVIDENCE:  `grep -n 'g_idle_add\|^fn emit_app_term' src/target/linux_gtk/app_io.rs` — `emit_app_term_clear` (line 487, doc comment "home the cursor, schedule a redraw") and `emit_app_term_set_cursor` (line 308, "store the cursor-visible flag and redraw") each call `g_idle_add` with `TERM_REDRAW_IDLE_SYMBOL` (lines 323, 530), the same snapshot-and-`queue_draw` helper `emit_app_term_sync` uses (line 124 comment). So on the Linux app backend clear/hideCursor/showCursor do present, as the three function pages say, and the overview and sync page's "one and only" is wrong for that backend. (Could not run a Linux --app build in this sandbox; the claim rests on reading the code.)
SUGGESTED: Pick one story and state it in both places. Either soften the overview and sync page: "term::sync is the one call that presents a frame in a terminal and in a macOS or Windows --app window; a Linux --app window also repaints on term::clear, term::hideCursor and term::showCursor" — and drop showCursor/hideCursor from the sync page's "touches the terminal not at all" list — or, if the Linux repaint is considered an implementation accident a developer should not rely on, delete the three "a Linux --app build repaints from this call itself" sentences and keep the overview's rule. The current state tells a reader two different contracts depending on which page they open.

### 2. Overview understates which code points term::drawGlyph skips
UNIT:      man-pkg:term
PAGE:      package-wide (overview vs drawGlyph)
CATEGORY:  overview-mismatch
CLAIM:     Overview: "term::drawGlyph stamps one glyph from an Integer code point; a value below U+0020 is skipped." drawGlyph page: "Control code points are skipped — those below U+0020 (including negative values), DEL (U+007F) and the C1 controls U+0080–U+009F … and so is any value that is not a Unicode scalar: one above U+10FFFF or inside the surrogate range U+D800–U+DFFF."
VERDICT:   misleading
EVIDENCE:  `sed -n 170,190p src/codegen/term/core/term/text.rs` — the glyph path branches to `inactive` for cp < 32, for 127 ≤ cp ≤ 159, for cp > 1114111, and for 55296 ≤ cp ≤ 57343. The drawGlyph page and its `codepoint` parameter description match the code; the overview's "below U+0020" is the only rule a reader of the overview sees, and it implies DEL, C1 and surrogates are drawn.
SUGGESTED: In the overview replace "a value below U+0020 is skipped" with "control code points (below U+0020, DEL and U+0080–U+009F) and values that are not Unicode scalars are skipped silently — see term::drawGlyph."
