### 1. The page never names the error that end of input raises
UNIT:      man-page:io/readByte
CLAIM:     "End of input is reported as an error, not as a sentinel value such as 0 or -1, which keeps every one of the 256 byte values usable as data."
VERDICT:   incomplete
EVIDENCE:  Probe `/tmp/plan-125-scratch/D-phase6/man-page-io-readByte/eof.mfb` (readByte under an inline `TRAP(e)`, run with `</dev/null`) printed `caught 77020003: Read operation reached end of file where a value was required.` and `is ErrEndOfFile`. The uncaught form (`ex/build/ex.out </dev/null`) printed `Error: 7-702-0003` and exited 255. The lowering raises it at the `_eof` label (`src/codegen/builtins/io/func_read_byte.rs:lower_read_byte`, `raise_error_into(symbol, "ErrEndOfFile", ...)`). The page names `ErrInputFailed` and `ErrInvalidContext` by name but leaves the reader to guess the code they must compare against for the one condition every pipe-fed program hits. §2 requires "every raisable error and the condition that raises it".
SUGGESTED: "End of input raises `ErrEndOfFile` rather than returning a sentinel value such as `0` or `-1`, which keeps every one of the 256 byte values usable as data. Trap it with `IF e.code = errorCode::ErrEndOfFile` when the end of a pipe or file is expected."

### 2. No Errors table renders, because the descriptor declares no errors
UNIT:      man-page:io/readByte
CLAIM:     (the absent `Errors` section — the rendered page goes from `Examples` straight to `See also`)
VERDICT:   incomplete
EVIDENCE:  `mfb man io readByte | grep '^Errors'` prints nothing, while `mfb man fs openFile` and `mfb man strings mid` render a Code/Name/Message table. The cause is `errors: vec![]` on the single `Implementation` in `src/codegen/builtins/io/func_read_byte.rs:register`, while `lower_read_byte` in the same file raises three errors: `ErrEndOfFile`, `ErrInputFailed` (setup path via `emit_configure_stdin_terminal`, and restore path via `emit_restore_stdin_terminal` in `src/codegen/io/terminal/io_terminal.rs`, which has its own `raise_error_into(..., "ErrInputFailed", ...)`), and `ErrInvalidContext`. All three were observed at runtime: EOF probe above; worker probe `worker.mfb` (readByte from an unsubscribed `ISOLATED FUNC`) printed `worker caught 77050019 ... is ErrInvalidContext`. Per `.ai/man-content.md` §0 a wrong derived table is a descriptor bug, not a prose fix. Note for the main thread only: `func_read_char.rs:67` and `func_read_line.rs:80` carry the same empty `errors: vec![]`; those pages are separate units.
SUGGESTED: Set `errors: vec!["ErrEndOfFile", "ErrInputFailed", "ErrInvalidContext"]` on the implementation so the Errors table renders, then confirm the prose names all three with their conditions (finding 1 supplies the missing one).

Everything else on the page checked out against the binary. For the audit trail: the example compiled and, fed `printf 'A'`, printed `65`. `loop.mfb` fed `😀\n` printed `240 159 152 128 10` then raised end of file, confirming byte-at-a-time with no decoding; fed `\xff\x00ABCD` it printed `255 0 65 66 67 68`, confirming 0 and 255 are ordinary data. `prompt.mfb` fed through a pipe emitted `prompt> ` before the byte, confirming the stdout drain. A Python pty harness (`ptyprobe.py`) sent a single `q` with no Return and the program returned `113` with no echo of the key, confirming the single-keypress, no-echo terminal claim. `worker2.mfb` with `thread::openStdIn(w)` returned `result 90`, confirming subscription lifts `ErrInvalidContext`. A grep of the rendered page for the banned memory vocabulary found nothing, and no sentence teaches an ownership model.
