# plan-153-B: `collections::repeat` — the in-place self-update arm

Last updated: 2026-09-24
Effort: medium (1h–2h)
Depends on: plan-153-A

This sub-plan makes `xs = collections::repeat(xs, v, count[, startAt])` update
`xs` where it stands:

- range writes are O(`count`);
- growing the list costs at most one grow;
- no copy of `xs` is made.

It applies at every site the self-update census covers:
- a local;
- a module-level global;
- inside a `FOR EACH` over `xs`;
- a `MUT` captured by reference;
- a record field;
- a `RES … STATE` field.

It also adds the census row the self-update policy requires. That policy says
a self-update-shaped builtin gets an arm or a proven exemption, never a
promise (`SelfUpdate` in `src/codegen/collection/assign/self_update.rs`).

**Correct behavior.** Two things must hold:

- **Allocation.** Take the `cases.tsv` harness statement
  `x = collections::repeat(x, 7, {M})`. It must satisfy the `arm` bound
  `count(2N) - count(N) < N/8`, and the result must equal plan-153-A's value
  path.
- **Failure atomicity.** A failing call must leave `x` exactly as it was.

## 3. Design Overview

`try_inplace_repeat_assign` runs in this order:

1. `resolve_self_update(site, value, "repeat", 4)`. The destination must be a
   `List`.
2. Evaluate `value`, `count` and `startAt`. Validate `count >= 0` and
   `0 <= startAt <= len(x)`. Raise **before any write**, which is what makes
   the call failure-atomic.
3. If `startAt + count > len(x)`, grow once, to at least `startAt + count`
   slots.
4. Overwrite `[startAt, min(len, startAt + count))` with the same primitive
   `set` uses.
5. Append the tail with the bulk-append shape.

For a fixed-width element, steps 4 and 5 become one store loop.

For field sites, use `FieldReach` like `set`/`insert`. A growing call on a
field that is not the last inlined field falls back to a rebuild, per
`field_realloc_admitted`. Put that site in `field_expect.tsv` as a rebuild,
not an arm.

**Correctness risk.** It concentrates in two places:

- **Aliasing.** `value` may read `x`, as in `x = repeat(x, collections::get(x, 0), 3)`.
  It must be evaluated and owned before the grow frees `x`'s old block. The
  `set` arm solves the same problem by materializing the item first; copy that
  order.
- **The string arm's decline** must stay by arity.

**Gate class:** behavior-preserving at the value level, but allocation counts
change by design. The gates are the census harness and the failure-atomicity
tests. The `.ncode` for programs that don't call `repeat` must not change: a
diff there means the matcher leaked into shared code.

Rejected alternative: **a `SelfUpdate::Exempt` row.** It doesn't apply,
because `repeat` builds its result from `x`'s block. That is exactly the case
the exemption excludes.

## Corrections

- **C1 — one `cases.tsv` row per signature.** The plan asked for three rows (in place,
  growing, `String`). `field_expect.tsv` is keyed on `(signature, site)` and
  `field_expectations` asserts no duplicate key, so a signature has exactly one line.
  The in-place and growing statements share the one row; the `String` element, which
  cannot share a row whose `x` is a `List OF Integer`, is measured by
  `tests/runtime/rt_repeat_self_update.rs` with the harness's own N/2N bound. The growing
  statement uses a constant start (`repeat(x, 8, 2, 3)`) rather than `len(x)`: at a field
  site `len(r.b)` reads the owner, which `field_realloc_admitted` treats as a possible view
  and rebuilds. The Validation Plan's coverage count is therefore 1 line, not 3.
- **C2 — the field expectations have no findings row.** `field_expect_gen.py` derives each
  line from plan-144's audit tables, which predate `repeat`. It gained a `POST_AUDIT` map
  (op → can-grow); `repeat` grows, so S3/T1/T3 are `rebuild:not-last-grow` and every other
  field site `arm`, the class `insert`/`prepend` have. This was Phase 2's regeneration task,
  pulled into Phase 1 because the harness panics on a row with no field lines.
- **C3 — graph-typed elements in place.** §3 did not cover an element type that reaches a type
  cycle. Writing `item`'s payload into `count` positions would share one graph `count` times,
  and a graph copy per position during the write loop can raise `ErrOutOfMemory` after `x` is
  partly written. The arm lowers `item` as a plain value (its graph stays with its origin),
  builds the `count` copies first as a private list (the value path on an empty list, then
  `own_collection_payload_edges`), writes element `i - start` of that list, and frees only
  that list's block (`free_intermediate_collection`, shallow for a graph type).
- **C4 — `seedSwarm` count.** The plan's "11 appends" does not match HEAD:
  `awk '/^SUB seedSwarm/,/^END SUB/' examples/wind/src/flow.mfb | grep -c "collections::append"` → 5
  (one `swarm` append and four trail appends inside the slot loop).
- **C5 — the wind acceptance instrument.** "alloc count per frame does not rise" was to be read
  from a whole-app 10 s `--debug` run. The report has no frame count, and three runs of unchanged
  source measured 6796872, 15331688 and 6837884 (the forecast download's progress dominates), so
  that number cannot show a per-frame change either way. Strengthened, not weakened: the changed
  code is measured deterministically by a probe program (Phase 3 check line), and the app run
  remains the builds-runs-draws check.

## Summary

The work is plumbing onto an established arm pattern. The risk is evaluation
order when `value` reads `x`, and the census makes a missing or wrong arm
fail loudly.
