# Ranking system

A per-row grade for how far MFBASIC is from its peers, designed so the grades
can order future optimisation work. Computed by `./benchmark/rank.py` from the
logs in `benchmark/baseline` (or any run's logs via `--dir`).

The reference comparison is **`mfb -O1` (the default level) against `c -O0`
(the default level)**, with **CPython as a second, independent reference**.

---

## 1. What is measured, and why not what you'd expect

Three properties of the data decide the whole design. Each was measured on the
committed baseline (`benchmark/baseline`, `run.sh 10`, Apple M2 Max). Every
table in this section is regenerated by:

    ./benchmark/rank.py --calibrate

### 1.1 Rank on the `min` column, not `median`

Benchmark noise here is **one-sided**: the OS can only ever make a run slower.
The three `mfb` logs (`-O1`/`-O2`/`-O3`) are three independent process runs of
nearly the same program — the median `-O3`/`-O1` speedup is only 1.05x — so the
spread between them is mostly measurement noise, and it measures each column's
stability directly:

| column | p50 | p75 | p90 | p95 | max |
|--------|-----|-----|-----|-----|-----|
| `min`     | 1.11 | 1.25 | 1.59 | 1.98 | 3.93 |
| `median`  | 1.24 | 1.70 | 2.47 | 3.00 | 12.46 |
| `average` | 1.77 | 2.79 | 4.97 | 9.00 | 81.10 |

Restricted to the 72 rows where the optimiser is provably inert (`-O2` and
`-O3` medians agree within 2%), so essentially pure noise: `min` disperses
1.06 / 1.26 / 1.62 (p50/p90/max) against `median`'s 1.08 / 1.43 / 3.06.

`min` is the most stable estimator on every percentile. `benchmark/baseline/README.md`
says to prefer the median; that is right for *reporting a time*, but for a
*ratio between two columns* the noise compounds, and `min` is the better
estimator. **`average` must never be used for a ratio** — a single descheduled
run moves it 5x.

### 1.2 Bands must be multiplicative and at least ~2x wide

Even on `min`, per-row noise is ~1.25x at p75 and ~1.6x at p90. Tighter bands
make rows flip grade between runs for no reason. Measured flip rate when the
same rows are graded on `min` versus on `median` (a proxy for a re-run):

| bands | flips | population |
|-------|-------|------------|
| 2x steps `[1,2,4,8,16,32]` | 41/250 (16%) | 58 51 44 30 26 16 25 |
| 2.5x steps `[1,2.5,6,15,40]` | 36/250 (14%) | 58 61 56 32 27 16 |
| 3x steps `[1,3,9,27,81]` | 30/250 (12%) | 58 76 52 36 21 7 |

2.5x steps are the chosen compromise: 3x buries a 10x row and a 25x row in one
band, 2x flips too often. **A one-grade difference between two runs of the same
build is not a signal.**

### 1.3 Absolute milliseconds are not a fair axis

The example ranking in the original request (`mfb <= c-O0 + 10 ms`) fails on
this data, and it is worth being explicit about why, because it is the
intuitive thing to reach for:

- **The rows are not sized comparably.** `c -O0` row times span three orders of
  magnitude (`min` column: p25 = 0.120 ms, p50 = 0.636 ms, p75 = 2.076 ms,
  max = 61.3 ms). 149 of the 250 comparable rows finish in under 1 ms in C.
- So the gate passes **213 of the 250** comparable rows — including
  `set (Fixed) remove`, which is **677x slower than C**. It cannot distinguish
  a correct implementation from a quadratic one. An absolute-millisecond
  gate grades the benchmark's arbitrary iteration counts, not MFBASIC.
- Several iteration counts are *deliberately* tiny (`benchmark/README.md`,
  "Arena-churn caveat"), which biases an absolute axis further.

The ratio `mfb/c-O0` is scale-free and is the only axis that survives this.
Absolute time still matters, but as a *confidence* input (section 3), never as
the severity axis.

## 2. The grade (the ranking)

For each row, `R_C = mfb-O1.min / c-O0.min`:

| grade | `R_C` | reading |
|-------|-------|---------|
| **S** | <= 1.0x | at or better than C `-O0` |
| **A** | <= 2.5x | same order as C `-O0`; within a compiler's normal spread |
| **B** | <= 6.0x | visibly slower, but no structural defect implied |
| **C** | <= 15x | a slow path — worth a look |
| **D** | <= 40x | a wrong-shape implementation |
| **F** | > 40x | an algorithmic defect (wrong complexity, or per-element allocation) |

Denominators are clamped at 0.001 ms, the log's print resolution, so a peer
that rounded to `0.000` reads as "at most 1 us" rather than "infinitely fast".

Baseline distribution over 480 rows: **S 117, A 104, B 110, C 56, D 37, F 56**.
So 69% of rows (331) are within 6x of C `-O0`, and 31% (149) are at C-grade
or worse.

## 3. Confidence (how much a row's grade can be trusted)

A grade is only as good as its measurement. Two *independent* qualities are
tracked, deliberately not folded into one label — they answer different
questions and a row can be weak on either.

**`baseline` — whose time was the ratio taken against?**

| | rule | rows |
|-|------|------|
| **direct** | the row has a real C and CPython peer | 250 |
| **proxy** | mfb-only row; baseline borrowed from the scalar sibling | 230 |

**`confidence` — was the row big enough to measure?**

| | rule | rows | use |
|-|------|------|-----|
| **firm** | `max(mfb, c-O0) >= 0.050 ms` | 451 | usable |
| **small** | 0.010–0.050 ms | 15 | ratio is real, the prize is microseconds |
| **noise** | under 0.010 ms | 14 | not a measurement; excluded from clusters |

**234 rows are both `direct` and `firm`** — those carry the weight of the
ranking. Everything else is reported but discounted.

**Proxy rows.** 235 of the 485 mfb rows are the `Record-`/`State-`/`key-`typed
container matrices, which have no C or Python counterpart at all. 230 of them
borrow the baseline of the same operation in the scalar section (`list
(Record-Fixed) insert` uses `list (Fixed) insert`'s C time). A record element is
genuinely more work in C too, so a proxy ratio is an over-estimate of unknown
size — the measured mfb-internal variant/scalar ratio is p50 1.00 but p90 3.73
(`--calibrate`). Treat
a proxy grade as directional. It is not noise: a proxy ratio of 1700x is a
defect no plausible baseline correction explains.

The 5 rows with no peer at all (`math fixed`, `vector fixed`, `mathpipe
finance`, `mathpipe money`, `crypto ed25519` — mfb-exclusive features) are
unrankable and dropped.

## 4. The CPython flag (an independent second opinion)

CPython is not a uniform bar, and using it as one is the flaw in "beat Python".
Measured `python/c-O0` on the 250 `direct` rows: **80 land within 1.5x of C,
and 69 of those are at or faster than C** — because those rows call a C library
through Python (`hashlib`, `re`, `base64`,
timsort) — `benchmark/README.md` warns about exactly this. So each row is first
classified by what its Python column actually is:

- `native-lib` (`py/c <= 1.5`) — the Python row is C code. **80 direct rows.**
- `mixed` (1.5–5x) — **43 direct rows.**
- `interpreted` (`py/c >= 5`) — CPython is really running its own bytecode
  loop. **127 direct rows.**

Then, when `mfb.min > python.min`:

- **`RED`** on an `interpreted` row — *a native compiler lost to a bytecode
  interpreter.* This is the single most diagnostic flag in the system: it is
  almost never a codegen-quality gap, it is a complexity or allocation defect.
  **62 rows** are RED (29 of them `direct`).
- **`LIB`** on a `native-lib` row — lost to a C library called from Python.
  Expected on `crypto`/`regex`/`sort` unless mfb claims its own builtin for it;
  informational, not damning. **144 rows** (66 `direct`).

`RED` is orthogonal to the grade and should be read alongside it: a `C`-grade
row that is also `RED` outranks a `D`-grade row that is not.

## 5. Element-type overhead (the axis with no caveats)

For the 233 measurable container-matrix rows, `mfb(variant).min /
mfb(scalar).min` compares mfb to itself: no borrowed baseline, no
cross-language assumption, highest confidence in the whole system. **36 rows
cost >= 2x and 18 cost >= 10x** to hold a record or state element instead of a
scalar, topping out at `set (State-Dynamic) add` at **702x** (32.3 ms vs
0.046 ms). Where a proxy grade is disputed, this axis usually settles it.

## 6. Ordering the work

Individual rows are the wrong unit — 149 C-or-worse rows are not 149 bugs. Rows
are clustered by **operation name across sections**, because one operation
failing in six containers is one runtime primitive, hence one fix. Each cluster
scores:

    score = SUM over rows of  w_confidence * w_baseline * log2(max(R_C, 1))
    w_confidence: firm 1.0, small 0.25, noise excluded
    w_baseline:   direct 1.0, proxy 0.5

`log2` because octaves are the natural unit of a speedup (a 4x row is worth
twice a 2x row, not four times), and the weights keep borrowed baselines from
outvoting measured ones. A cluster with no `direct`+`firm` row is printed but
marked `[proxy only]` — it has never been measured against a real peer.

Top of the baseline queue: `set` (54.6), `remove` (33.8), `removeKey` (30.0),
`removeAt` (28.1), `insert` (27.5), `prepend` (25.6), `isSuperset` (24.5). Six
of the seven are element-mutating collection operations and six carry RED rows
(`removeAt` carries none) — one coherent finding about collection mutation
rather than seven separate ones.

The report's last section lists C-or-worse rows that `-O2`/`-O3` already speeds
up >= 1.5x, so effort is not spent re-doing what the optimiser does at a higher
level.

## 7. Using it

    ./benchmark/rank.py                    # full report
    ./benchmark/rank.py --csv > rows.csv   # per-row, for diffing two runs

Rules for reading a result:

1. **A one-grade move between runs is noise** (section 1.2). Confirm a claimed
   improvement with `run.sh 50` before recording it.
2. **Never compare across hosts.** Ratios are more portable than times, but
   `c -O0` and `mfb -O1` do not scale identically across machines.
3. **Fix clusters, not rows.** A row's grade justifies attention; the cluster
   score justifies the schedule.
4. **`RED` before `F`.** A grade-F row with no RED flag may just be a missing
   optimisation; a RED row is a defect.
